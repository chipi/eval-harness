# 0.8.1, in full

The full notes of 0.8.1; its section in the [CHANGELOG](https://github.com/chipi/eval-harness/blob/main/harness/CHANGELOG.md)
is the short version. **Some results move**, and the first section lists each, by project, with what to do. No data format,
fingerprint version or scorer changed, `evh migrate --check` finds nothing to do, and nothing is re-scored: the same runs
are read by one rule where each reader used to work the fact out for itself
([RFC-041](../rfc/RFC-041-one-source-for-each-fact.md)). What a project must change is in
[UPGRADING](https://github.com/chipi/eval-harness/blob/main/harness/docs/UPGRADING.md).

## Results that move

Three projects upgraded to 0.8.0 on 2026-11-23 and each found one bug: a cap of $0 printed as "NONE", a measure its goal
says is lower-is-better printed as "higher", and a pass added back to an arm counted as another arm. They had one cause,
and the fix is a rule each fact is read by, so these results move with it.

- **This repository.** `triage_local_x3_nemotron_35_bolt_e4b_v1_20261030T201736Z` repeats `…_20261030T192906Z` with equal
  data, deployment, settings and adapter. It now joins that run's arm, which reads two runs: `evh arm-list` shows 669 arms,
  not 673 (the arm's `repeats` row, and its three re-scored copies, are gone). Its numbers and every ranking it is in can
  move. The three scifact repeats (`--purpose repeat --of`) differ from their originals in deployment and adapter, and
  stay under `repeats`; the eight triage `--repeat 3` sets name no `--of` and are unchanged.
- **The fleet (fleet-eval-data).** The arm `triage_v2_station_dc3315d_v1` on `orrery_triage_v1_labelled_v2` goes from 2 runs
  to 3: its repeat, made with `--purpose repeat --of`, was read as a separate arm. This is the fix asked for. Its pair tests
  and its goal page on that dataset can change. (From RFC-041's read-only pass over a copy of the project: five of its 447
  scores change arm.)
- **The podcast project (podcast-scraper-eval-data).** `wer` on `curated_5feeds_dev_v1` (68 arms) and
  `curated_5feeds_benchmark_v1` (8 arms) was ranked higher-is-better, because nothing there declares it and the harness did
  not know it. `wer`, `cer` and `der` now read lower-is-better wherever nothing declares otherwise, so every ranking and test
  on `wer` there turns the right way up. A goal's or an adapter's declaration still wins.

For every project, by rule:

- **A repeat joins its arm.** A run made with `--purpose repeat --of RUN` is read in RUN's arm when it is the same
  measurement taken again: the same system and dataset, and equal data, deployment, settings and adapter parts in the two
  fingerprints. A later harness build does not keep it out (the whole hash changes with every release's code) and is named.
  The arm then averages them per item. A repeat that differs in a part, whose original is gone, or whose original is itself
  read under `repeats` stays there, with the reason; `evh run --purpose repeat` says which before its first call and in its
  last line. A repeat of a repeat follows `--of` to the first run. A closed round's numbers never change: a repeat made
  after it closed is listed in its "since then".
- **A repeat set is what the runs record.** `--repeat N` records `repeat_index`; that, or a joined repeat, makes a set. A
  run named `foo_r1` is not a set member by its name: two hand-named `_rN` runs are two plain runs, and V8 fails them
  unless `duplicate_ok` lists the pair. Two `--repeat` invocations of one system are two sets: runs that carry the same
  `repeat_index` are not one set, and V8 fails or notes them the same way.
- **An arm has one value: the mean over its items.** `evh leaderboard` took the mean of the runs' means, which differs from
  `arm-show` and `metric-show` (the mean over items, repeats pooled per item) where an arm's runs score different item counts.
  It now reads the same number (`model.runs.pooled_mean`); the per-run `spread` is unchanged. On the fleet project two arms move,
  none changes rank: `bugfix_issue_67dcceb_flash_k0_v1` on the silver reference (`oracle_pass` 0.125 to 0.0833) and
  `triage_v1_dc3315d_v1` on `orrery_triage_v1_labelled_v2` (`tokens_in` 3611 to 3602).
  A `--repeat N` set recorded with `purpose: repeat` and no `of` (0.7 and earlier) is read as it was in 0.8.0: under `repeats`, as an arm of its own beside the plain run.
  Only a repeat that names the run it repeats (`--of`) joins that run's arm, and `evh run --purpose repeat` now refuses to write one without `--of`.
- **An arm is read against one reference in every view.** The catalog read an arm against the reference of its latest run (the
  greatest `created_at`, then run id: one function, `model.runs.latest`) and the commands read every run of it. `leaderboard`,
  `pair-test`, `cost-report` and the others that read runs by arm now do as the catalog does: a run scored against another
  reference is left out, never averaged in, and named in a `WARNING` line. Four readers picked "the latest run" differently
  (by name prefix, by run-id order, by `created_at`); `judge-score` and the repeat hint now use it too.
- **One rule says which way is better** (`_runs.direction`), by the first of these that answers: a goal that declares the
  measure (for a dataset, a goal that lists it, then a goal the runs name: a goal that names the dataset speaks for it, while a
  run's `goal` only says what the run was made for; a goal with `datasets: []` is heard only through a run that names it, and by
  a question with no dataset); what the runs record (the adapter's `METRIC_DIRECTIONS`, `import-run --asc`, then declared kinds:
  descriptive is neutral); the name; the default, higher, for a measure nothing declares. The names: lower is better for
  `cost_usd`, `total_cost_usd`, `tokens_in`, `tokens_out`, `total_tokens_in`, `total_tokens_out`, `latency_ms`, `latency_s`,
  `wer`, `cer` and `der`; neutral for `output_words`, `output_chars`, `lines`, `chars`, `n_items` and `reasoning_tokens`.
  `run-compare`, a study (a study on `cost_usd` keeps the cheaper trial, not the dearer) and the adapter's catalog views asked
  separately before. `leaderboard`, `run-compare` and `goal-leaderboard` print a `NOTE` when a ranking rests on the default,
  and `evh validate` notes each goal measure and primary metric that does. V14 fails two goals that give one measure opposite
  directions on one dataset.
- **A measure whose datasets disagree reads "mixed"**, with each dataset's answer, on the metric pages and in
  `metric-list`; each dataset's arms sort by its own direction.
- **A descriptive measure is "neutral"** in the leaderboard's heading and in its `--json` `direction`, not "higher is
  better".
- **A baseline is per goal.** The datasets page names each goal's baseline (`goal: arm`), not the latest promotion of any goal
  as "the" baseline; a goal's page and `goal-leaderboard` show the baseline that goal promoted.
- **Without `--metric`, a command reads the measure that decides on the dataset**: the goal's, when a run records it, else
  the runs' primary metric (`leaderboard`, `pair-test`, `family-test`, `rank-stability`, `holdout`, `period-compare`, the
  sheet, the inspector's first metric). Where a goal's measure is not the primary metric, the default changes. `pair-test`
  refused where `leaderboard` read the goal.
- **A NaN, an infinity or a None score is a failed item, on read as on write.** `evh run` records it as a failed item with its
  reason (`score q is not a number: nan`), scores it as a failed item is (0 on most measures) and never averages it;
  `--resume` calls it again. `rescore`, `judge-score`, `sheet-import` and `import-run` refuse such a score by name;
  `arm-smoke` says the item was not scored. A run recorded earlier with one is read the same way, as a failed item scored 0,
  where the tests left the item out and said how many (`non_finite`): the verdict on old data with such a score can move
  (an arm that was significant on N-1 items can stop being so on N). No mean prints "nan". An arm that failed every item
  says so on the goal page.
- **A cost nobody reported is unknown, never $0.** `arm-smoke`'s full-run projection says "cost unknown" instead of
  `about $0`; a run where only some items reported a cost records `cost_coverage: {items_with_cost, items}`, and its
  `total_cost_usd` is of those items. The cost charts leave an arm whose cost is unknown off the
  cost axis and name it, where they read it as 0, and refuse (`not-enough`) when no arm has a known cost. A recorded cost of 0 shows `$0`, and "not recorded" shows "—": a free local
  model's cost cell was "—". Every amount is written by one function (`$0`, two significant digits under a cent, four places up
  to a dollar, two above).

## New refusals

Each refuses by name before anything is spent or written, and each is a fact a reader follows
([RFC-041](../rfc/RFC-041-one-source-for-each-fact.md) F7, owner decisions of 2026-11-23). A run already recorded is read as
before.

- **A run, system or reference id that is not plain** (`--run-id`, `import-run --system-id`, `reference-promote --name`):
  ASCII letters, digits, `.`, `_`, `-`; no path, no space, no unicode (`bad-argument`). The arm ids `<label>/<dataset>/<system>`
  could not be split back otherwise.
- **`--purpose repeat` with no `--of`** (`bad-argument`; `--scratch` is exempt). An old repeat with no `of` is read under
  `repeats`, as before.
- **A repeat's, retime's or pair's `--of` that names another system's or dataset's run** (`mismatch`). A repeat of a retired
  arm's run in an open round is refused too (`bad-argument`): it would bring the arm back.
- **`import-run` with a `--reference-id` that is not there** (`not-found`), a `--reference-tier` that contradicts the id
  (`mismatch`; the id says the tier), or a tier with no reference (`bad-argument`).
- **`arm-smoke` with a `--goal` or `--round` that is not there** (`not-found`), or a `--round` with no `--goal`: the spend
  would be dropped from the round without a word.
- **`run-promote` of a build recorded with `dirty: null` and no `source`** (a run from before 0.8.0 says nothing of its tree),
  as it refuses a build git could not read and as `label-from-run` does (`--allow-dirty` overrides). It let such a run through.
- **`evh leaderboard --goal G` where no run records the goal's measure** refuses with exit 7, the new kind `nothing-measured`, and
  names what the runs record. It was `not-found`, which says the goal is not there. Without `--goal` it ranks each arm on its own headline with one `NOTE`.
- **A run with no goal once the goal policy says so.** From `required_from` in `data/goals/policy.yaml`, `evh run` (not
  `--scratch`) and `evh import-run` refuse a run with no `--goal` (`bad-argument`), where validate's V14 only failed it later.

New things:

- **`evh import-run --goal G`** records the goal an imported run answers.
- **The run field `cost_coverage`** (above), in `metrics.schema.json`.
- **V29 holds every `of`**: a repeat's, a retime's or a pair's must name a run of its own system and dataset (a failure
  otherwise). It notes, and does not fail, an `of` whose run is gone (the repeat is read under `repeats`; the note names the
  `run.json`) and a round that recorded a repeat under `repeats` where it now joins its arm (the round reads what it recorded).
- **V30 fails a broken link the harness wrote**: a run the harness scored whose reference (`gold/` or `silver/`) or label
  set is not there, named with the file that holds the link. A goal's `datasets:` entry that names no dataset (a plain id,
  prose or a pattern) is a warning, a plain id's saying it fails from 0.9, and an imported run's reference outside `data/`
  is a note, so a project whose goals are written in prose, or that imports runs against its own reference folders, still
  validates (the podcast project's R8 run). V16 notes each such reference too. `evh validate` is V1 to V30.
- **`goal-new` and `goal-set` warn**, and `run-promote` too for a run that records no value of the goal's measure, when a goal's
  primary measure is recorded by no run on its datasets or its direction is neither `lower` nor `higher` (a decision rule such as
  `non_inferior` is not a direction). V14 says the same in the same words.

## Public surfaces

- **A prompt is shown publicly only with `--publish prompts`** (owner, 2026-11-23). A system's `params.prompt` (any prompt text
  its yaml carries) and a recorded prompt file's text (`prompt-show --text`, `prompt-diff`) are served on a public server,
  in the public MCP and in the catalog export only with `evh catalog-serve --publish prompts` or `catalog: {publish:
  [prompts]}` in `config.yaml`. Otherwise `params.prompt` reads `(prompt text: not published here)`. A reference's promotion
  reason and a prompt version's note stay public.
- **A read a public server drops refuses in-process too.** `judge-verdicts` (the judges' reasons), `comparison-item`,
  `comparison-items`, `sheet-show`, `exposure`, `sealed-counts`, `validate`, `data-ls`, `data-show`, `label-mutants` and
  `label-coverage-show` were refused by the routes and the tool list only: an in-process call with `EVH_PUBLIC` set and no
  hosts got them. They now answer `not-allowed`.
- **One question, "is this the public server?"** (`_visibility.public()`): the inspector's item route and the sheet asked the
  hosts alone, the comparison the hosts or the environment. And a dataset whose file is missing or unreadable is hidden on a
  public server, where it was shown.

## Added

- **The Workbench, read-only, for visitors to a deployment**
  ([RFC-039](../rfc/RFC-039-workbench-read-only-for-visitors.md)). A public server serves `/workbench/` and the
  `/api/v1` operations that only read, the same set the public MCP server answers, under the same text rules
  (`text: hidden`, `--publish`) and rate limit. Everything that writes, spends or runs a model, `POST /estimate`,
  `/jobs` and `/session` is refused at the server. The page draws no control that acts, says on every screen that it is
  a read-only view, and leaves out of its menu the screens whose only job is to act. `evh catalog-serve --catalog-at
  PATH` says where the deployment serves the catalog (`/catalog/` on this repository's), so the Workbench's links to
  it go there; the default is `/`. A project's own server is unchanged.
- **Where the judge disagrees with the gold, per item.** An item disagrees when its own term of the judge's validation
  figure (`evh judge-validate`) is under that figure's chance level: Kendall's tau under 0 (grade), top-1 under the
  item's chance (pick), pair agreement under 0.5 (pairwise). The inspector's item view says "judge vs gold: agrees" or
  "disagrees"; the sheet marks the rows and filters them (`only=judge`); `evh comparison-items` and `evh sheet-export`
  take `--judge-disagrees`. A public server shows it only when it publishes both outputs and references.
- **A fact dump, to compare two versions on one project** (`tools/facts_dump.py`, in a checkout; `make facts-dump`). For every
  (dataset, arm, metric) it collects the value, the items behind it and the direction word; for every arm its run ids, its
  latest run, the reference it is read against and its cost state (unknown, zero or an amount); for every dataset each goal's
  baseline and whether its text is shown on a public server. It reads `evh <command> --json` and nothing else, so it runs
  beside any installed `evh` of 0.8.0 or later, and `--diff old.json new.json` prints each fact that changed, old to new. The
  same collection is the CLI's reader in `tests/test_reader_agreement.py`, which asks the API, the MCP reads, the catalog's
  export and the inspector for the same facts and fails when two disagree.

## Changed

- **`evh catalog-serve` renders each page when it is asked for**
  ([RFC-040](../rfc/RFC-040-catalog-rendered-on-request.md)). A write through the Workbench, the API, MCP or the command
  line is on the next page opened: no `catalog` job runs, and no page shows the data from before a rebuild. The server
  needs no `evh catalog` first. A page is rendered from one model of the data, kept until the data changes (2.3 s to
  make on this repository's runs); the home page, the goals page and each goal's page are rendered ahead after a change.
  `evh catalog` writes the same pages as files, byte for byte, for a host with no server; it is also faster (13 s to
  8 s here), since a goal's decisions and the model records are read once for every page that shows them. `GET /api/health`'s `catalog` is
  now `{mode: "on request", state: idle | failed, built_at, prepared, failed}`: `building`, `job` and `queued` are
  gone. A deployment with `--public` is unchanged.
- **The inspector names arms by one rule everywhere.** The sheet used to keep a shared prefix; it now drops only the
  dataset's own words, as every other view does. A path name keeps its system id (`rescored-…/…/triage_baseline_pro_v1`
  reads `baseline_pro_v1`); two arms left with the same name keep their paths.
- **A scatter's names never cover a dot or another name.** A name sits beside its dot where it covers neither; else it
  moves to the nearest clear place within four lines, with a leader line to its dot; else the caption names it.
- **"See the cost first" shows the figure.** Each arm's `ESTIMATE ~$…` and the cap the Workbench will send are shown
  above the dry run, which is folded. Before, they were below the fold of a scrolling box, and the line shown for the cap
  was the estimate's own (`NONE`), not the one typed.
- **`evh runs-list` tells an unknown tree from a clean one.** A run made with `EVAL_BUILD_REF` set, or brought in by
  `evh import-run`, records `build.dirty: null`; `runs-list` showed it as clean. The table now marks it `?` with a legend
  line, and `--json` carries `dirty: true | false | null`. A record with no `build` reads as unknown (it raised
  `KeyError`). Read null as "unknown" if you read `dirty` from `runs-list --json`. Git that cannot say records `null` too, not
  `false` (clean); promotion and `label-from-run` refuse only a build git was asked about and could not read, and `run-compare`
  says "unknown".
- **`evh run --dry-run` says what runs.** The system line names the project's adapter (`adapter adapters/headline.py`), not the
  bundled adapter's `echo`, which a custom adapter does not read; `--json` gains `adapter`, and `provider` is null when the system
  sets none.
- **`metric-show`, `metric-list` and the metric pages say two facts, not one.** "decides" is the goals whose primary measure it
  is; "weighed as an axis by" the goals that take it as one of their other axes (cost, speed or their own). A measure a goal
  decides on is weighed by none, and the words say so.
- **`pair-test` and the goal page say what the data cannot.** `pair-test` prints the smallest p its n items or clusters can
  reach when that is above the level (3 items: 0.25; `min_p` in `--json`), and a pair whose differences do not vary prints
  `n/a`; a clustered test that cannot run says how many items and clusters it had.
- **No "nan" is shown.** `cost-report` prints an unknown ratio, and `rank-stability` an unknown rho or winner rate, as "—" (null in
  `--json`); a bill against nothing recorded is flagged.
- **`evh leaderboard` of a dataset whose goal reads a measure no run records** (a prose name such as "WER vs human transcript",
  where the runs record `wer`) ranks each arm on its own headline and prints one `NOTE` naming the goal, its measure and what the
  arms record; before, it refused, so a project of imported runs could rank no dataset. With `--goal` or `--round` it still
  refuses, and names what the arms record.
- **Which day it is is the UTC date, in one place** (`_common.today()`): a deployment's staleness, the home and period views, the
  goals' period and the view cache used the machine's local date, another day for some hours of each.

## Fixed

- **`check_hf_source.py` (the examples' rerun job)** retried any error for 30 seconds, a 4xx included. It retries a 5xx,
  a dropped connection and a timeout for about two minutes, says each retry, fails a 4xx at once, and ends in one line,
  never a traceback.
- **`make site`** removed `site/public` and wrote in place for two minutes, so an interrupted build left it mostly
  deleted. It builds beside it and swaps in a whole build.
- **A cap of 0** (`EVAL_MAX_COST_USD=0`, "spend nothing") was shown as `NONE — set EVAL_MAX_COST_USD` by
  `evh run --dry-run` and as `NONE — a sweep can bill without limit` by `evh env-check`, and the dry run's `--json`
  said `cap_usd: null`. Both show `$0.00` and that it spends nothing; `cap_usd` is `0`. The cap itself was always
  enforced.
- **Which way is better, for a measure no run records yet.** `evh metric-list`, `evh metric-show` and the catalog's
  metric pages said "higher" for a measure that only a goal names, whatever the goal's `direction`. They now go by the
  goals deciding on it, then the name table (`cost_usd`: lower). For a measure that runs record, see "Results that move".
- **A study's `stop` with one bound is valid** (`trials`, `usd` or `wall_h`; it needed `trials`, or both `usd` and `wall_h`), and
  a stop of `usd: 0` is one (`is not None`, as opening the study reads it).
- **A goal's page ranks each measure the way that measure goes**, on each dataset, where it read the goal's `direction` for every
  row; a judge's group reads on the judge's score.

## What the beta projects' fact dumps found

The homelab, podcast and fleet projects each ran the fact dump above under 0.8.0 and under this release, and send back the
difference. Every line of a difference that is not explained under "Results that move" is to be listed here, with its cause,
before 0.8.1 is tagged. None is listed yet.

## The repository and its release

- **A merge to main deploys nothing.** `deploy-prod.yml` runs only when dispatched, with the commit it is for; its first
  step refuses any other commit. `make deploy-dry`, then `make deploy`, which refuses unless a dry run of that same
  commit passed. The repository variable `PROD_AUTO_DEPLOY`, which let a push deploy, is deleted.
- **A release's notes are short.** From 0.8.0 a CHANGELOG section is at most 4,000 characters and links its full notes
  here, in `docs/releases/` (checked by `site-check`). 0.8.0's 161,773 characters moved to
  [0.8.0.md](0.8.0.md).
- **A check that every reader gives one answer.** Source checks fail when a reader works a fact out itself (which way is better, which
  runs make an arm, the day, the public gate, a cap); a table of statistics edge cases (every item failed, disjoint items, every
  cluster of one, a 3-item dataset); look-alike projects of the beta projects' shapes (an import with prose goals, a fleet's repeat
  set that lost a pass, a zero-price bake-off with a custom adapter), run through every read command on both stores; a sentinel in
  every private field, searched in every public read, page and export. Tutorial 9 writes a custom adapter end to end and
  `guide-check` runs it. `make upgrade-check` installs the last release, makes a project on it, installs this build over it and
  reads the project.
- **Tests that fail only for a reason.** The Workbench's paid run is tested end to end against a local provider that
  bills (estimate, cap, round budget, spend, `build.dirty`, `runs-list`, 390 px). The inspector and the real catalog
  are browser-tested on SQLite as well as files. Every browser test lays pages out in one bundled font (Lato, SIL OFL
  1.1), so a layout check fails at the same width on any machine. Two tests that failed under load wait on the state they
  need: a timing check compares structure, not two clocks, and a page load is asked again only when Chromium reports the
  machine's network changed.
- **A release tag could move.** The `release tags` ruleset let a repository admin bypass its `deletion` rule, and a tag
  deleted could be created again on another commit, as `v0.8.0` was on 2026-11-22 (from `448d34baa` to `094aa680a`,
  before any Release named it). The ruleset now has no bypass: it holds for an admin too, and RELEASING.md says how a
  mistaken tag is fixed on purpose.
