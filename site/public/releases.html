v0.4.0

See your runs, not only tables of them. evh catalog builds static pages over a project's runs, and evh catalog-serve runs an inspector that tests chosen arms against a baseline and shows one item's outputs beside its reference. A project on the harness's layout needs no code; one with its own layout writes one adapter. Goals record what an evaluation is for; items carry the typed fields a project declares, and can live at a pinned URL. The paired test now lives in one place, evaluation_harness.stats, exact at 30 items or fewer. Upgrading can move a result only where pair-test or family-test ran on 30 items or fewer, in a wins count or an order on a lower-is-better metric, or where --exclude-dataset named a dataset whose items are not .txt files under data/sources/<id>/ (all below), and adds no dependency. Design: ADR-0002, ADR-0003; how to upgrade: UPGRADING.

This repository now deploys the harness on its own example experiments:

  • the catalog and run inspector are public at catalog.evals.humancopilot.eu;
  • the public site, the harness and its findings, moves from GitHub Pages to the same server;
  • the docs move to docs.evals.humancopilot.eu, and old /docs/ links redirect there.

The deployment files are in infra/ (runbook: infra/README.md). They are not part of the package.

The example experiments keep one record per arm, the latest: the rescored and re-parsed runs are folded into data/runs as derived runs, and DailyMail's bart_s is its fp32 run (coverage 0.4048; the fp16 run read 0.4039). CNN's bart_s stays the fp16 run, the one the judge's verdicts were made on. The reports state the current figures only; their correction logs are gone (git keeps them). Two published statements were stale and are restated: SciFact's qwen_s e5-first against the e5-first leader is +0.0178, p 0.10 (it read +0.0092, p 0.36, from the pre-fix run), and DBpedia's 56-item dev slice, over today's 28 arms, puts bert_base_fy alone at the top rather than 13 arms in a tie.

Added

  • Everything the catalog and the inspector show is a command. evh datasets (one dataset: its versions, references and arms), evh references (one: who wrote it, from which run, what is scored against it), evh metrics, evh goals (one: its arms per dataset) and evh inspect --runs … (the inspector's verdicts, conditions, --where/--by on fields, --item for one item's outputs beside the reference). Same adapter, same computation: the numbers are the pages'. Each is also a make target.
  • The catalog says what every number is measured against. A metrics page (what each metric measures, which way is better, where it is recorded, which goals decide on it) and a page per reference (who wrote it, from which run, every arm scored against it); every metric and reference on the pages links there. Each arm's row says what it is scored against, and rows scored against silver, by a judge, or against the reference the arm wrote itself are tinted; a judged arm reads "judge <scorer>", no longer "gold". A goal page flags the arm that wrote the reference it is scored against, so it is never the leader. The inspector's charts section is "analysis", and its verdict rows carry the same tints. Actions are compact and tinted.
  • Long tables page. Every catalog table and the inspector's per-item table show 10 rows, with "show 10 more" and "show all"; the filter and the sort work over every row, and a link to a row opens the table at it. The verdict tables stay whole: their Holm thresholds are read together.
  • Dataset versions keep their lineage. evh dataset-create --dataset-id x_v2 --from x_v1 records where a version came from and the item ids it adds, removes and changes (derived_from in the dataset file); validate V2 fails a version whose parent is gone. The catalog links versions both ways with what changed, and a version no arm has run on yet gets a page when it is linked to one that has.
  • The inspector says whether the compared runs ran under the same conditions, from their fingerprints: the machine, library versions, the harness, the scorer (adapter code), the items and the reference's bytes. One line when all match; otherwise the fields that differ, arm by arm, with a warning when the scorer or the reference bytes differ (different measurements) or latency is compared across machines. A dataset page names each arm's machine when its arms ran on more than one.
  • METRIC_DESCRIPTIONS in an adapter, one sentence per metric, is recorded on every run (metric_descriptions in metrics.json) and refreshed by evh rescore; the harness describes its own metrics (cost, tokens, latency, judge scores).
  • A run becomes a reference: evh reference-create --from-run <run_id> (make reference-create RUN=<run_id>). The usual way to get references is to run the expensive model as an arm, read its results, and score the cheaper arms against what it wrote. Until now that took a second paid pass (--config), whose outputs could differ from the run you read, and the reference did not say which run it came from. --from-run copies a finished run's outputs and calls nothing; the manifest records the run, its config, fingerprint, build and cost. It refuses what run-promote refuses (a dirty tree, an unknown build), an unfinished, derived or other-dataset run, and --tier gold (gold is what a person wrote or checked).
  • reference-create refuses an empty output, and outputs that stopped at max_tokens, by either path (--allow-cut-off for outputs that end at the cap by design). A frontier arm at max_tokens: 80 wrote 19 of 20 summaries cut off mid-sentence and one empty reply, and they were frozen as the reference with no word.
  • The leaderboard marks the arm that wrote the reference it is scored against (arm *, and a note): that row is graded against its own outputs.
  • reference-create says when gold exists (new runs keep scoring against gold; how to rescore against the new silver), and to commit the reference before the next run: an uncommitted reference makes every later run dirty.
  • A newcomer scenario for every release (SCENARIO): a fresh project, the published docs only, a summariser and a classifier with small CPU models, cheap hosted LLMs, a frontier reference and a judge, browsed in the catalog, under $1. RELEASING runs it before the merge.

Changed

  • Exact p-values at 30 items or fewer. pair-test and family-test now count the two-sided sign-flip p over all 2^n sign patterns when a pair shares 30 items or fewer, instead of estimating it from 20,000 seeded permutations. Above 30 items the estimate is unchanged, bit for bit, including family-test's single stream across opponents. Near a threshold the estimate could land on either side of it; the count cannot. This can move a result: - in this repository's reports: none moved. All 200 report claims re-derive unchanged, because every published pair and family test is on more than 30 items; - in the tutorial (6 items): pair-test reads 0.0312 (was 0.0330), and the family test 0.0938 against lead1 and 0.3125 against author (lead2_noisy's is unseeded and moves with every run). The verdicts are the same (GUIDE steps 6 and 8); - in your project: re-run pair-test / family-test on any pair with 30 or fewer shared items. Whether a verdict near its threshold moves depends on your data.
  • pair-test says which it did: (exact, all 2^n sign patterns) or (20000 permutations).
  • family-test's cache key includes stats.py, so a cached answer from 0.3.0 is recomputed.
  • validate V4 no longer passes what it did not check. A materialized copy that has lost an item file now fails; it used to be skipped. A dataset with no materialized copy on the machine (materialized data is not committed, so a CI job has none) is named as not checked, and the ok line says how many were checked, e.g. "3 of 14 datasets materialized here". A project whose materialized copy is incomplete goes red where it was green.
  • The bundled adapter names its primary metric (PRIMARY_METRIC = "overlap_f1"). New runs on it record primary_metric: overlap_f1. The leaderboard already ranked them by it, first by name; it no longer prints that the metric was "chosen by sort order", and the catalog and the inspector open on it. Runs made before keep what they recorded.
  • docs/GUIDE.md is a walkthrough in your own project: install the package, evh init --tutorial, then every step with evh. It used to run inside a checkout of this repository, with make.
  • The default metric is the one your runs recorded. pair-test, family-test, holdout and rank-stability defaulted to coverage, the summarisation example's metric: in any project that does not score it they found no runs, or crashed. Without --metric they now read the primary metric the runs on the dataset recorded, and refuse, naming the recorded metrics, when none did.
  • evh self-test in a project checks the installed harness: the paired test's own suite, then the tutorial end to end in a scratch folder (dataset with fields, runs, pair-test, rescore, validate, catalog). It used to run this repository's development suite, which checks this repository's reports and failed 52 checks in every project; in a checkout it still does.
  • A metric's direction is inferred, not remembered by a flag, by one rule for every command and the inspector: a flag, else the goal the runs name, else the adapter's METRIC_DIRECTIONS (new, recorded on the run) or import-run --asc (a field nothing read until now), else the name (cost, latency and token metrics go down); V14 fails a goal that contradicts its runs. So lower is better without --asc for pair-test's "A wins", family-test's wins and "ahead", the leaderboard's order and significance block, holdout and rank-stability. leaderboard --sort latency_ms ranked the slowest arm first. p-values do not change (the tests are two-sided); --asc and --desc override. This can move a wins or "ahead" count, and an order, on a lower-is-better metric; no published claim is on one (200/200 re-derive).
  • validate checks the project's own run directories. V7, V8 and V9 read this repository's six directory names, so a project's data/runs-adjudicated was never checked; V10's scorer sources were this repository's example paths. They are project policy in <data>/validate.json (committed, floors, scorer_sources, duplicate_ok); without it every git-tracked runs* directory is checked (validate_floors.json is gone).
  • The package holds the harness, not this repository's tests. The wheel shipped ~14,500 lines of tests and report checkers; they are in harness/tests/ and harness/tools/ in the checkout. self-test's own suite (test_stats.py) still ships. A run's code_sha256 hashes the code that can move a number (the run-writing commands and what they import, read from the source), so editing a test no longer shows in run-compare as a confound; 0.4.0 runs record a different value from 0.3.0 runs. The deploy installs the inspector from the wheel too.
  • Refusals and arguments. Every command refuses with ERROR: … on stderr and exit 1 (four printed to stdout); a command that takes no arguments refuses one with exit 2 (validate, self-test and five checkers ignored them). RUNBOOK: exit codes and every environment variable.
  • The bundled adapter refuses an unknown provider: (a typo fell back to echo and recorded the echoed input as the model's output), and records what an OpenAI-compatible provider billed when the response carries it. One price rule for it and the judges.
  • One run record, one format; a derived run says what it was derived from. rescore, judge-score and the SciFact re-parse write derived: {kind, from, at, with}, their own created_at, and source_created_at. rescored_from, rescored_with, judged_from, judged_with, judge_label, reparsed_* and primary_metric_asc are gone, and nothing reads them: a 0.3.0 derived run is read as a measured one. Every field the harness writes is declared in metrics.schema.json, and V1 fails a run record with any other (0.3.0's import-run --asc wrote primary_metric_asc, which nothing read; 0.4.0 writes metric_directions, which every command reads). EVAL_GOALS_DIR reads goals from outside the data root; latency_s is a speed metric, lower is better, as latency_ms is. A goal may name no dataset (one checked by a gate) and may set direction: non_inferior, a guard that ranks nothing (no significant drop against a baseline). rescore no longer records a metric it kept as dropped (rescore_dropped_metrics named whichever key a loop ended on).
  • --resume-unverified is gone. experiment-run --resume refuses rows written before 0.4.0 (no _extra); experiment-run writes _extra on every row, so its own rows resume.
  • The integration seam is adapter.py at the project root. An arm whose config names no adapter: uses it, recorded as adapter.py, and the bundled adapter only when there is none. The docs lead with the pin and evh init rather than a copied harness/.
  • Importing the package changes nothing. .env is read when a harness command starts, not on import, and the project's paths resolve on first use, so an adapter's tests or a notebook can set EVAL_HOME after the import. evaluation_harness.catalog_adapter reads no path at import, and its load_adapter is load_catalog_adapter.
  • Configs, judge scorers, judging sets and verdicts have schemas, and validate V1 checks them. A config key other than config_id, dataset_id, params, adapter, goal and format fails (a mistyped key was read by nothing and passed).
  • A baseline carries what its number means: run-promote records the run's reference tier, adapter and fingerprint hash, runs-list --baselines prints the tier and adapter, and V6 fails a baseline that no longer matches its run. A 0.3.0 baseline fails V6 until it is promoted again. Promoting replaces the baseline: the copy archived to data/baselines/superseded/ and the supersedes field are gone, and git keeps the old one.
  • A command run from a project's subfolder finds the project: without EVAL_HOME, the root is the nearest directory up with a data/ folder (it was the current directory, so evh validate in a subfolder read an empty project).
  • The judge panel is a command, evh judge (it sat beside the package and could not run from a pin); the tutorial kit ships tutorial/judge_panel.yaml.

Fixed

  • The inspector reads only arms and references the catalog lists. It asked the adapter's arms_of about any path a request named; an adapter that maps a path to itself (the podcast repo's did) let compare read outside the data tree (runs=../../.git). A request may name an arm, or a path that selects arms (a run directory), but only arms the adapter's arms() reach, and a reference references() lists.
  • A catalog nav entry may carry a CSS class as a fourth element (hide-sm hides it on a phone), and the inspector page names the command that serves it (serve).
  • evh rescore and evh silver-calibrate in a project that pins the package. A run made with no adapter: uses the bundled adapter and records it as scripts/adapter.py, a path that exists only in a checkout, so both failed with "adapter not found" in every pinned project on the default adapter (0.2.0 and 0.3.0 alike). They now score with the package's own copy, the one that made the run, through one shared lookup. Found by following the GUIDE in a brand-new project.
  • The "next, run this" hints name a command you have. Every one said make …, a target only a checkout of this repository has; through evh they now say evh … (the first was GUIDE step 1's "Next: make dataset-materialize"). Two were wrong in a checkout too: an empty baselines list suggested make promote (the target is run-promote), and an empty runs list suggested make demo, which a project without the bundled sample data cannot run.
  • evh catalog-serve on a port another program holds says so and suggests --port, instead of a Python traceback.
  • rescore onto another reference no longer claims the references changed. Moving runs from silver to gold (--reference-id) compared the gold files' hash with the silver files' and, as they always differ, wrote references_changed_since_measurement: true into every re-scored run and printed "the reference files have CHANGED". The move is recorded as before (reference_id_at_measurement); the flag and the warning are kept for the same reference's files changing. No committed run in this repository carries the false flag.
  • Commands that assumed a checkout, each found by running every evh command in a project that pins the package: - rank-stability crashed (set.intersection()) instead of saying no arm had the metric; on a lower-is-better metric it named the worst arm the leader; with too few items for two halves it now says so. - --exclude-dataset (pair-test, family-test, holdout, bootstrap-test) read data/sources/<id>/*.txt instead of the dataset file: wrong for any item that is not a .txt, any dataset from a manifest, any project keeping sources elsewhere, and "nothing excluded" was then reported as true. - The leaderboard's metric kinds, run-compare's, and the classification report's label parser looked for a run's adapter in the checkout only; they now find the bundled one in the package, as rescore does. - bootstrap-test on a gold set of free text (summaries) treated every summary as a class and would have reported a macro-F1; it now refuses, and its "too few items" refusal names the threshold and the opponents. - catalog-serve printed its address without flushing, so under a log file or a process supervisor the line did not appear; --build-dir outside the project was a traceback, now a refusal; self-test --help ran the whole suite instead of printing help.
  • The catalog counted a dataset's items from the harness's own path, not the adapter's, so a project with its own layout got "the most items any arm scored". It now asks the adapter (dataset_items, optional).
  • The bundled adapter's anthropic provider failed every call with the anthropic SDK 1.x, which dropped the temperature= keyword: a TypeError before the request was sent. The temperature now travels in the request body, so the request is the one every SDK version sends. A self-test checks the call against the installed SDK's own signature. Found by mypy.
  • A manifest URL could read a local file. dataset-create --manifest fetched any scheme urlopen accepts, so a file:///… row was copied into the item cache and pinned, although a dataset's schema allows only http(s). Every fetch now refuses other schemes before reading anything. Found by bandit.
  • The judge panel judged placeholder text. Every finalist, real runs included, was scored on "Synthetic item i for <run>". It now reads each finalist's stored outputs, finds runs where every command does (EVAL_RUNS_DIR, the project), ranks by their primary metric, and refuses a lower-is-better one rather than promote the worst.
  • rescore could record the bundled adapter's metric kinds in a project's run: two registries named loaded adapters differently, and the lookup fell back to the bundled one. One loader (_adapter.py), keyed by the resolved file.
  • import evaluation_harness.judging failed in an installed package (No module named 'stats'), and importing catalog_adapter beside it loaded _common twice.
  • holdout's significance block had no direction, so on a lower-is-better metric it ranked the worst arm first.
  • Checks that could not fail, or did not run: self-test's cost-cap control turned any failure into a skip; check_terminology was failing and nothing ran it (it is in make test now); make -C harness docs was a no-op (eight targets were not .PHONY).

Added

  • evaluation_harness.stats. Standard library only, and the one place the paired test lives: - exact_p and sign_flip_p; - holm, with a declared family larger than the p-values passed; - exact_ci, an interval for the mean difference that agrees with the test: none at 5 items or fewer, where no shift can be rejected; - compare, every arm against a baseline with verdicts in words; - compare_by, the same test within each group of items, Holm-corrected over every group and arm together; - ranks, pearson and spearman (average ranks for ties; a constant input returns constant, NaN unless you pass another), which the judging, rank-stability and report-check scripts share instead of keeping their own copies.

It has its own test suite, scripts/test_stats.py, run by make test.

  • The exact count is ~4x faster (0.03 s at 30 items, was 0.11 s): the sign-pattern sums are built by doubling a list instead of enumerating each pattern. The same sums, so the same p. The exact interval bisects to ~1e-9 of its span, not ~1e-14: 1.4 s at 30 items, was 11 s. It is shown to 3 decimals.
  • evh catalog and evh catalog-serve (make catalog, make catalog-serve). - The catalog: static pages over a project's runs, by dataset, built into .build/catalog/. Each dataset page lists every arm with its headline number, and links to the inspector for one arm, or for all the arms on one metric scored against one reference. - The run inspector: a server on 127.0.0.1 that tests any arms on one dataset against a baseline with stats.py, so it gives the same p as pair-test on the same pair. It shows the verdicts, charts of the per-item scores and differences, and, for one item, each arm's output beside the reference. - The same rules as everywhere else: - Arms on different dataset_ids are refused. - On a metric scored against a reference, an arm scored against another reference than the baseline's (silver against gold, say) is named and not tested against it; cost, latency, tokens and length compare across references. - The static pages carry counts and means only, never an item's text. - The server answers only to a 127.0.0.1 Host. It serves only the catalog and the data tree, and no dot-folder in either. - An adapter is the only project code needed. catalog_adapter.Adapter lists the questions both tools ask. The built-in HarnessAdapter reads the harness's own layout (runs*/, runs-judged/, references/): an arm is one config on one dataset, its repeats averaged per item. A project with another layout names its own adapter in config.yaml (catalog: {adapter: path/to/file.py:Class}) or passes --adapter.

- A public mode (evh catalog-serve --public HOST), for a deployment behind a reverse proxy that serves the static pages: - it answers only the named host; - each client gets --rate requests a minute; - at most --max-arms arms in one comparison; - two computations at once, every answer cached; - errors never show the server's internals; - --warm computes, at start, every comparison the built catalog links to.

evh catalog --link LABEL=URL adds the deployment's other sites to the nav. - CSP-clean: no inline script or style. The theme script is a file, and the legend colours are set from JS.

Tests: tests/test_catalog.py (54 assertions), run by make test.

  • Goals: what an evaluation is for (data/goals/<goal_id>.yaml, schemas/goal.schema.json). - What a goal says: who uses the output, the decision it informs, the measure that decides (and which direction is better), the output formats it accepts, its datasets and their roles, and optionally min_items, the fewest items a winner may rest on. - Configs name their goal (goal:) and may declare the format they ask for. - experiment-run refuses an unknown goal before it runs. - The run records both, outside the fingerprint: they change what a run answers, not what it measured. - run-promote carries both onto the baseline. - validate V14 fails: - a goal that breaks its schema, or whose goal_id is not its file name; - a config, run or baseline naming a goal that does not exist, or a format the goal does not accept.

A dataset smaller than a goal's min_items gets a note. - Optional until a project opts in. Set required_from: YYYY-MM-DD in data/goals/policy.yaml, and every run created from then on must name a goal. A project upgrading changes nothing until it sets the date. - In the catalog: a goals page, and a page per goal. On each of the goal's datasets it ranks the arms that record the goal's measure. An arm under min_items or in a format the goal does not accept is flagged and never the leader. Each arm links to the inspector, tested against the leader. - This repository's six experiments have goals (data/goals/), and so does the tutorial (tutorial/goals/tickets_summary.yaml). No date is set here, so nothing already committed is held to one.

Tests: tests/test_goals.py (14 assertions), run by make test.

  • Item fields (data/fields/<fieldset_id>.yaml, schemas/fieldset.schema.json, ADR-0003). The harness defines no field: a project declares its own in a field set, and any number of its datasets name it. - Types: text, number, integer, boolean, date, duration (seconds; h:mm:ss accepted), url, and choice with its values; a field can be required and public. - dataset-create --fieldset ID --fields FILE attaches values from a CSV or JSONL, one row per item_id, and refuses an undeclared column, a mistyped value, a value outside a choice, an unknown item and an empty required field. --update-fields corrects values on an existing dataset. - Not the identity. A run's fingerprint hashes item ids and bytes only, so a corrected field invalidates no run; the dataset records fields_sha256 beside them. - validate V15 fails a field set that breaks its schema, fields with no field set or an unknown one, an undeclared or mistyped value, a missing required value, and a fields_sha256 that does not match (a hand edit). - In the catalog: each field with its coverage, and a summary of its values only when it is public. In the inspector: an item's fields beside its outputs; a filter on any field; a breakdown by a choice or yes/no field, tested per group with stats.compare_by. A public deployment answers with public fields only. - The adapter protocol gains an optional item_fields(dataset).
  • Items fetched from a pinned URL. dataset-create --manifest FILE takes one row per item: item_id, source_url and source_sha256 (empty: fetched and pinned now), and field columns. dataset-materialize downloads each into .cache/items/ and refuses bytes that hash to anything else, as it refuses a changed file. A transient failure is retried like a provider call; a host that needs a header gets it from EVAL_FETCH_HEADERS (that host only, never on a redirect elsewhere, never written into a dataset). With --update-fields, an empty cell clears a value.

v0.3.0

Re-measure what you already have. Stored outputs can now be scored again by LLM judges, as an optional pass that never touches a committed run: evh judge-score, for any text task you declare (what an item is, what the outputs are, the dimensions, the scale). The harness refuses a judge until the scorer names, for each judge, a committed run that measured it against human ratings; it runs at least two judges from different vendors blind, measures their position bias and noise, and stores every verdict so a rerun costs $0. The tutorial has an offline, $0 judging step (GUIDE step 10). Upgrading from 0.2.0 changes no committed run or score and adds no dependency. Design: ADR-0001; what it found here: the judging page.

Added

  • evh judge-score (and make judge-score). Re-measure an experiment's frozen outputs with a validated LLM judge, billed, cost-capped and resumable. It runs from the installed package in a project that has only its own data directory, scorer, prompt and runs: the prompt builder, reply parser, tau-b and Spearman, and an OpenAI-compatible judge client (LiteLLM proxy, OpenRouter direct, per-judge base_url / api_key_env, billed cost read from the response, retries) are in evaluation_harness.judging, with no dependency on examples/.
  • The judge scorer artifact (data/scorers/<id>.yaml): two or more judges from different vendor families, the task, the prompt (with its sha256), the protocol, a validation block and a cost cap.
  • Any text task, declared in the scorer. An optional task block names what each item is (source_label), what the arms wrote (output_label), the dimensions the judge scores and the scale; a prompt writes {n} where the number of outputs per call goes. Without a task block a scorer judges SummEval's news-summary task (ARTICLE, SUMMARIES, four dimensions, 1-5), byte for byte as before. A declared task is hashed into the judging set.
  • A judging step in the tutorial (docs/GUIDE.md step 10): harness/tutorial/scorers/tickets-judge-v1.yaml re-measures the tutorial's arms with two fake judges, offline and $0, through the refusal, the dry run, the pass and the leaderboard.
  • A validation gate. A scorer runs only if its validation block names a committed run for each judge whose metric equals the stated value (and is at least min_metric, when the scorer sets one) and whose model, temperature, reasoning, provider, max tokens, prompt file and prompt sha256 are the judge's. The gate checks that a validation exists and is current, not that it transfers to your outputs. Otherwise --unvalidated runs it and labels every number "unvalidated judge". provider: fake judges (offline, free, for testing a scorer) can never pass the gate.
  • Judging sets and stored verdicts. One item is the article plus every arm's output, arm identities hidden, order shuffled by a seed; the set is hashed into its id and frozen in data/judging-sets/. Every reply is stored per call in data/judge-verdicts/, with its scores, so a rerun resumes and re-reading costs $0; a reply that is not bare JSON scores, or repeats 8 consecutive words of the item or an output, is kept only as its hash, since a judge that reasons aloud can copy the source. A different arm set is a new set, never an append. A block retried with --retry-unparsed keeps the earlier calls' cost in its record.
  • Controls. A position check (a second shuffle that re-forms the blocks) and a noise check (a repeat on a subset), plus per-judge agreement and a self-family flag, in summary.json.
  • Adjudicated gold re-measurement (repository tooling, examples/_shared/adjudicate.py, not in the package): a committed adjudication file overwrites only the disputed items of a local gold reference set to make a new reference version, and rescore re-scores every run against it for $0, the old reference kept beside it.
  • Judge validation on published human ratings (repository tooling, not in the package): validate_judge_goyal.py (Goyal, Li & Durrett 2022) and validate_judge_zhang.py (Zhang et al. 2024, crowd ratings of 19 LLM-era summarisers) check a scorer's judges against people. The ratings are downloaded when the check runs, pinned by sha256, and never committed; the committed records hold article ids, the judges' replies and scores, and hashes; a reply that is not bare JSON scores, or repeats 8 consecutive words of the source, is kept only as its hash.
  • validate V11-V13. V11: every judging set's stored hash is the hash of its content. V12: every stored verdict names a real set, item, pass and block, and its n is that block's size, and every committed judge reply (verdicts and validation records) is bare JSON or kept only as its hash. V13: every judge scorer loads, is structurally valid (its task included), and its prompt file resolves and renders. They read the configured data directory.
  • judge-score judges every arm on the dataset by default. A scorer's arms_match, --match and --arms narrow it, and it warns when the arm set mixes config versions (_v1 and _v2 of one arm are judged as two arms).
  • A scorer's prompt.file resolves against the project root, then the scorer file's own directory, then (in a checkout of this repository only) the repository root.
  • Judged runs carry no reference_tier, since a judge reads no reference: the source run's tier is kept as judged_with.source_reference_tier, and leaderboard says the scores come from a judge, with its label.
  • A refused judge call stops the pass cleanly. A call refused, or still failing after its retries (a provider's own budget guardrail answering 403, for example), stops the pass the way the cost cap does: every stored verdict is kept, the partial result is projected and labelled, and the same command resumes.
  • Scorer checks. task.scale must be whole numbers, and a prompt with both {n} and SummEval's fixed count phrases is refused (the phrases would keep saying 16). V13 renders each prompt at 2 outputs, so a prompt that cannot be rendered fails there, not at run time.
  • Experiment-level results this enables are reported in the repository's reports (the summarisation experiment re-measured with two pairs of SummEval-validated judges, not confirmed by people on those outputs; AG News and DBpedia against adjudicated gold); none of them is in the package.

Changed

  • leaderboard's precision note no longer fires on values that are exact small-integer fractions (a mean of 1-5 ratings over two judges and four dimensions is in eighths); scores rounded on the way to disk still get it.
  • Nothing that scores a run changed: committed runs and their recorded hashes are untouched, and the committed summarisation judging set rebuilds from its stored verdicts with the same id.
