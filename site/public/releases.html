v0.8.0

Added

  • "If your system is plain code" (INTEGRATION, the fleet's feedback 19 and 26): what an item holds for code that reads external state (its world at decision time), why one run is enough, a correctness goal beside a regression guard, the item as the unit judged, links between items folded into an outcome, and outcomes joined by time and order rather than by a key the outcome may not carry.
  • Code under test as a record of its own (the fleet's feedback 27): a model record with kind: code holds its repository and its versions (commit, deployed windows, the faithfulness a replay measured), with no aliases. Its Models page row shows its latest commit and how many versions were checked, never "not onboarded"; its page and evh models --model list the versions. Validate V18 names a version listed twice.
  • A private inspector behind a proxy (homelab, 2026-11-05): evh catalog-serve --behind-proxy HOST[,HOST] serves the whole local inspector (pages, items, outputs, references) to the named Hosts as well as this machine, with --bind 0.0.0.0 in a container behind a team's own proxy; no rate limit and nothing withheld, unlike --public. The data page's writes are not served through it.
  • A metric of the whole run (the fleet's feedback 20): an adapter's optional score_run(items), called once with every item's output, reference and scores, returns named numbers (pairwise precision and recall of a grouping, say) that no mean of items can be. They are recorded in scores and named in run_metrics; the leaderboard shows them, rescore recomputes them, the comparison shows each arm's value untested, and pair-test/family-test refuse them by name.
  • How far outcome rules label a dataset (the fleet's feedback 31): evh label-coverage --dataset-id D --capture C --map rules.yaml applies label-from-capture's rules without writing: labelled now, skipped by design, not yet mature (with each item's maturing date), matched by no rule (with the outcome fields they lack), not in the capture; per rule, the items it takes now and when mature. A read tool on the local MCP server.
  • Items, not item-runs (the fleet's feedback 33): run --repeat ends with how many items every repeat scored the same on the primary metric, named near-copies when nearly all are, and the items to read against the item-runs; pair-test names each arm's runs and their per-item agreement (repeats, in JSON too) and says each item counts once.
  • A dataset already cited gains its lineage (the fleet's feedback 16): evh dataset-create --dataset-id D --from P --lineage-only records the dataset D was made from and what changed, recomputing its version, with its items and the rest of its record untouched; a second parent, a split side and a loop are refused.
  • A round records its harness code (the fleet's feedback 17): round-open records the harness version, commit and measuring-code hash it opened on and says so; evh rounds shows it and names each run of the round that ran on other harness code, with how to run it on the round's (a worktree at its commit, or its version pinned).
  • A round's baseline can be named (the fleet's feedback 22): evh round-open … --baseline <config_id or run id> records the run the round starts from when the dataset has no promoted baseline (arms carried in with --keep), so pair-test --round and evh rounds read its arms against it instead of refusing ("records no other baseline run"). round-open says which run the round starts from.
  • A regression guard (the fleet's feedback 28): expect_identical_to: <config_id> in an arm's config says its runs must reproduce that config's, item for item and output for output (the same code at another commit). evh validate V5 reads such a pair as the agreement asked for, not as an inert knob, and fails the guard when they differ. Recorded on the run, outside the fingerprint.
  • A project's data in SQLite, a project's choice (RFC-025). Files stay the default; store: sqlite in config.yaml, or EVAL_STORE=sqlite, keeps everything under data/ in one database, data/project.sqlite (write-ahead logged; a run's outputs and rows committed as they are produced), and nothing under data/ on disk but it. Every command, the catalog and the inspector read and write through one module (_store); a test fails on path I/O anywhere else. evh data-migrate --to sqlite|files moves a project either way, every file read back by its sha256; on this repository's data the round trip gives back every file byte for byte. validate V23 names a project in both. Python code is never in the database.
  • The Configure page (PRD-016, UXS-004, ADR-0027), for a SQLite project that sets configure: true: a menu item of its own after Inspector, served by a local catalog-serve. Without it the catalog is built and served with no Configure part at all; a files project cannot turn it on (it is edited in its files; validate V23 names it). make serve [STORE=sqlite] [CONFIGURE=1] stands the whole thing up on 127.0.0.1, in SQLite from a copy of this repository's data. The page: everything a project keeps under data/ and its settings (arm configs, goals, fieldsets, judge scorers, model records, failure-mode lists, validate.json) created, edited and deleted there, in a form built from each kind's schema: a field per key, the right control for its type, the project's datasets, goals and model records suggested; no YAML to type. A setting is saved only after it passes the check (it matches its schema, its id is its file name but for an arm config), each problem shown at its field; a save keeps the file's comments and every line it does not change (every setting in this repository written back unchanged is the same file, and 5,159 one-value edits kept every comment). Harness-written data is shown read-only with the command that writes it; a run is deleted whole. It is the one catalog page that writes, on this machine only: a public server answers no /api/data call. The same in the terminal: evh data-ls, data-show [--fields], data-put [--set KEY=VALUE] [--unset KEY], data-rm. A save runs evh validate before and after it: what the project's own check newly refuses (a scorer with judges of one family, a config naming a goal that does not exist) puts the file back and comes back as the save's problems. Rebuild the catalog on the page rebuilds the other pages beside the served ones and swaps them in. Every kind of setting can be created, changed and deleted through the page alone, so a project in SQLite needs no terminal to manage its settings. In SQLite mode it is how a person's settings get into the database without data-migrate. New dependency: ruamel.yaml (owner yes, 2026-11-06), which writes a setting back with its comments.
  • schemas/validate.schema.json and schemas/goal-policy.schema.json: the validate policy's keys and the goal policy's required_from, written from what validate and goal_policy read; the data page builds their forms from them. A judge's params.family, which judge_score requires two of, is in the scorer schema.
  • Tests that know when items are related. --cluster FIELD on pair-test, family-test and bootstrap-test, and cluster: FIELD on a goal's dataset (used by the goal page, evh goals, the inspector, rounds and --round): items that share a value of the field (one thread's comments, one incident's decisions) count as one. The sign-flip test flips one sign per cluster, the interval is cluster-robust above 30 clusters, the bootstrap draws whole clusters. Tested items one by one, related items made p too small: in a simulation of 12 clusters of 5 with no real difference, the item test called 45% of them significant, the cluster test 4%. validate (V14) refuses a goal whose cluster field no item carries.
  • The contender test is shown. evh goals has a column "contender test (within the margin)" (p, its Holm threshold, shown or not, or "too few"), --json carries it per arm (noninferior), the goal page's cell says it, and evh pair-test --margin M runs it for any one pair.
  • What a goal can detect. Its decision says the smallest margin a contender could be shown within, with its number of candidates and items or clusters (80% power): on ag_news, 29 candidates on 200 items need about 0.10, so its 5% (0.048) admits nobody. axes.quality.reference: baseline tests contenders against the promoted baseline ("no worse than what runs now") instead of the leader.
  • How repeats combine, named. success_criteria.primary.reduce on a goal, and --reduce on pair-test and family-test: mean (the default, as before), majority or at_least_K for 0/1 scores (at_least_1 is pass@k's question). The catalog keeps each item's repeats beside their mean.
  • Agreement over every label set, and where people disagree with the reference. evh labels --dataset-id D gives Krippendorff's alpha over all the sets together (three or more), with a 95% bootstrap interval (it is Krippendorff's 0.743 on his 2011 example); --contested lists, per item, how many people's sets agree with the gold reference. The pairwise alpha now counts labels in one pass (it compared every pair of labels, 4 × 10^8 at 10,000 items).
  • Judges: length bias, a 0/1 start, and why a rubric changed. A judging's summary.json gives each judge's length_bias, Spearman's rho of its score with the output's length in words (the committed judge-summ-v1: 0.23 and 0.29; judge-summ-v2: 0.02 and 0.21; both summaries re-summarised from their verdicts, $0, nothing else changed). The RUNBOOK recommends scale: [0, 1] to start a project's own judge. A scorer that replaces another says so: supersedes: and why:, checked by validate (V13) and printed by judge-score.
  • How an arm fails: failure modes and tags. A project names its failure modes once (data/failure-modes/<id>.yaml); evh inspect --sheet … --fill tags --modes <id> writes a sheet with a failure_modes: cell beside each arm's output, evh sheet-import … --tags <name> --modes <id> reads it back as a tag set (checked against its key, never edited); evh tags and the goal page count each arm's modes, and the sheet shows each item's in an <arm>: failure modes column. ok marks an output read and found fine; a blank cell was not read. validate V21 checks the lists and the sets.
  • A dataset can name its licence. Optional: dataset-create --licence ID, or evh dataset-describe --dataset-id D --licence ID later (a licence or description change is no new version). evh licences lists the SPDX ids a line each (--search, --json, an MCP tool); unknown and LicenseRef-<name> are allowed; validate V22 refuses others. The committed Hub datasets carry the licence their Hub page states (2026-11-05): ag_news unknown, cnn_dailymail Apache-2.0, dbpedia_14 CC-BY-SA-3.0, few-nerd and scifact CC-BY-SA-4.0, summeval MIT.
  • Where the items came from, the same for every source. A dataset record has a source block: provider, ref, url, revision (the source's own version), config, split, gated, description_sha256 and item_url (one item's page, with {row} or {item_id}); each item its source_row. dataset-create reads it from a fetcher's data/sources/<id>.rows.json; the profile and the catalog link items from the record, no longer from that file. validate V22 checks it. The committed Hub datasets and their profiles were migrated by evh dataset-migrate from what their profiles recorded; revision and gated were never recorded for them and are null.
  • A dataset card. The datasheet questions, answered in a card block under Croissant RAI 1.0's property names (dataUseCases, dataCollection, dataAnnotationProtocol, dataBiases, dataLimitations, …, twenty in all): evh dataset-describe --card-template prints them with their questions, --card FILE records the answers. No new version; validate V22 checks the keys.
  • Dataset sources: one interface for every place items come from. evh dataset-create --source NAME --query JSON reads a source: a class with describe(query) (source block, licence, description, card, features) and items(query), found as importers are (built-in folder and manifest, a project's data/dataset_sources/NAME.py, or path.py:Class). Its items are written to data/sources/<id>/, never over files already there.
  • A dataset as Croissant 1.1. evh dataset-card --dataset-id D --format croissant writes the record as Croissant JSON-LD (licence, version, source url, parent, the card as rai: properties, its files with their sha256, the items as a record set with typed fields); without --format it prints the card as text (also an MCP tool). A required property the record cannot give is named, never invented. Not run through mlcroissant. --format hf-readme writes the card as a Hugging Face dataset README.
  • A dataset from a Croissant description. --source croissant reads any Croissant file or URL whose record set is columns of one parquet, CSV, JSON or JSON-lines file (its sha256 checked), with the description's licence, version (as source.revision) and rai: card. A FileSet is refused, naming its format: Hugging Face's descriptions keep their parquet in one, whose files only the Hub can list.
  • pyarrow is a dependency (owner, 2026-11-05), to read parquet: pyarrow>=15, installed with the harness.
  • A field set proposed from a source. evh fieldset-propose --source NAME --query JSON --fieldset-id ID turns the features a source describes into a field set (types mapped, few-valued text proposed as a choice from a sample), printed for a person to read; --write writes it, never over one that exists.
  • A dataset from the Hugging Face Hub, pinned. --source huggingface --query '{"ref", "split", "text", …}' reads the Hub's parquet conversion of a split at one commit (source.revision), each file checked against the Hub's sha256, with the card's licence and metadata, and each row's viewer page as its link.
  • Publishing a dataset to the Hugging Face Hub. evh dataset-publish --to huggingface --query '{"repo": …}' writes a new repo, private by default (items as parquet, the record, the card as README), reads it back by sha256, and records where it went on the dataset. Hidden datasets are never published. huggingface_hub>=0.26 is a new dependency (owner, 2026-11-05). Checked live: a private repo published, read back and deleted.
  • Datasets from Zenodo and OpenML. --source zenodo reads a record's table file (md5 checked, the record id as revision); --source openml reads a dataset's parquet copy with its version and typed features.
  • Datasets from Kaggle, without kagglehub. --source kaggle reads a table file of a dataset's zip at a version through Kaggle's own API (public datasets need no credentials), with its licence mapped from Kaggle's name.
  • The examples fetch through the huggingface source. Their shared reader (examples/_shared/hf_rows.py) reads each split's parquet conversion at a commit pinned once a fetch, each file sha256-checked, instead of the datasets-server's /rows (whose 2026-11-02 outage held back a release); the retry ladder, the parquet fallback and the fetchers' --delay are gone. The rows were checked equal to /rows at 21 places across the 8 splits the fetchers read, and the 12 committed Hub datasets fetched fresh match every frozen hash and gold checksum. The examples cap pyarrow below 26, which refuses the NumPy 1.x they pin on Intel macOS (18.1 to 25.0 checked).

Changed

  • The paired tests take their normal limit from 10,000 units (ADR-0028). From 10,000 items (or clusters) the sign-flip p is erfc(|z|/sqrt 2) with z = sum d / sqrt(sum d^2), and the contender test's bootstrap-t p is 1 - Phi(T), instead of 20,000 permutations and 9,999 resamples; a simulation over seven kinds of data (tools/large_sample_check.py) found them within the resampling's own Monte Carlo error there, and not at 1,000 to 5,000 for heavy-tailed or sparse data, so below 10,000 nothing changes and no committed result moves. pair-test and family-test say which (method: exact, sampled, normal limit, in the text and --json; family-test a p_method per row). A p from the limit can be 0.0 (it prints <0.0001). A family that mixes sizes keeps its other opponents' p's: the one random stream moves past a large opponent as if it were drawn.
  • Every evh command keeps the p's it draws in <project>/.cache/evh-p.jsonl (EVH_P_CACHE; an empty value turns it off), as evh mcp did: goals right after catalog reads them instead of drawing them again (142 s to 0.4 s on a 1,000-item, 50-arm project).
  • Resampled tests are drawn at once in child processes: a catalog's, a goal's and a comparison's bootstrap-t's and sign-flips are found first, drawn in parallel, and read back, the same p's bit for bit (each is seeded by its data or its seed). The 1,000-item, 50-arm project's catalog took 16.3 s instead of 150.4 s, goals --goal --json 12.5 s instead of 147.7 s, with the same JSON and the same pages. Small projects are drawn as before, and so is everything in a container under one whole CPU (the quota is read, as cpus: 0.5 hides it from the core count); EVH_WORKERS sets the number, 1 turns it off.
  • A dataset page lists 200 items a page, the rest on pages beside it (d/<dataset>~items-2.html, ...): the 10,000-item page was 13.8 MB, now 0.32 MB. The page's filter reads its own page; evh dataset-items lists all.
  • The agent skills put a setting in with evh data-put and read one with evh data-show --text, in a temporary folder, so they work in either store and never touch a folder of the project's own.
  • A run's outputs are one file (RFC-024). outputs.jsonl, a line per item (item_id, text, sha256), appended as each output is produced and rewritten in dataset order when the run completes, replaces the outputs/ folder of one file per item. Re-scores, judgings and sheet imports no longer copy their source's outputs: they read them through derived.from. Every module reads outputs through one function. evh run-migrate moves a project's runs (--dry-run first); in this repository it turned 94,796 files into 305 (harness/data/ from 106,492 files to 12,001), every output and V5 signature checked equal before and after. A derived run records its source's directory (derived.from_dir) and reads only that run; validate V23 names a run left in the old layout or a derived run whose source is gone. A resume from a run that kept no row checkpoint no longer crashes (_Resumed read _extra from an empty row).
  • A dataset's version means something. version is MAJOR.MINOR, two integers (1.10 follows 1.9), computed from the lineage when the dataset is made: 1.0 for a first dataset and for each side of a split (which names its parent's version, split.from_version); from a parent (--from, dataset-extend), MINOR + 1 when items were only added, MAJOR + 1 and MINOR 0 when any was removed or changed. A licence or description change is no new version. validate (V22) recomputes it; evh dataset-migrate writes it for records made before (every committed dataset is 1.0 by the rule, as it was). Neither key is in a run's fingerprint: no run moves.
  • One failed item no longer stops a run (owner, 2026-11-05). An item whose call fails (not transiently) is scored as an empty answer (0 on most measures, or the adapter's score_failure(reference)), marked failed on its row, listed in metrics.json's failed_items, and called again by --resume; the run goes on. A 429 or a timeout that outlasts the retries now stops the run with 75 like an unreachable server (it used to end in a traceback), and more than 5 failures that are also over 20% of the items called stop it with ERROR (failed).
  • A contender is shown no worse than the leader (ADR-0026). It had to be "not significantly different", which more arms are the fewer items there are, and frugal then recommended the cheapest. Now a one-sided non-inferiority test against the leader decides, Holm across the candidates: Tango's score test for 0/1 scores at any size, the bootstrap-t from 100 items or clusters for other scores, "too few items to call a tie" below. A strategy is a default margin: balanced 5% of the leader (was 2%, with the old test), frugal 10% (had none), quality_first the same quality; a goal's axes.quality.margin wins, and validate notes each goal on a default. Recommendations move on goals whose contenders the old rule over- or under-counted: on this repository's 7 goals, scifact recommends deepseek_s (was the free e5_base, not shown within 10% once 18 arms are corrected for), ag_news bert_base_ta and triage its leader (both were undecided).
  • Each exit code has one meaning (RUNBOOK, Exit codes). The cost cap that stops evh run or judge-score early exits 4 (was 2, which is also a usage error); a run that measured nothing exits 7 (was 1, which is also a refusal); a server that could not be reached exits 75 (was 1); a check that ran and found problems exits 6 (was 1): validate, self-test, env-check, importer-check, arm-smoke, model-onboard, deploy-sheet --capture; a sweep in which some runs failed exits 5 (was 1). evh exits 70 for an error nothing caught (a traceback) and 130 on Ctrl-C, without a traceback.
  • Every refusal names its kind: ERROR (<kind>): <why>, the kind one of twelve (RUNBOOK, Refusals): not-found, bad-argument, would-overwrite, mismatch, invalid-file, not-materialized, not-enough, not-public, not-allowed, not-configured, failed, missing-dependency. A script or an agent reads the kind, which stays when a message is reworded. The project's AGENTS.md (evh init) says what to do for each exit code and the common kinds.

Fixed

  • The comparison swapped an asked metric in silence: inspect --metric M (and the inspector's metric=) on runs with no per-item score of M compared another metric and did not say so. It now says M cannot be tested, gives each arm's recorded value, and names the metric compared instead.
  • dataset-create --update-fields kept only part of the record: it rewrote the dataset with its items, description, source, licence and lineage, and dropped its card, tags, split block, hidden-text flag, extended_from and made_from. Every key it does not set is now kept.
  • A judge that runs out of max_tokens is stopped after 3 calls, not after the whole pass. A reasoning judge that spends its tokens thinking replies with nothing, every time; judge-score said so only at the end, after every call was paid for (the 0.7.1 newcomer run: tutorial 3's judge at 400 tokens). Now a judge whose first 3 replies all come back empty at the token limit stops the pass (STOPPED EARLY), keeps what it stored, and prints the hint.
  • The newcomer scenario and tutorial 3 commit what judging writes (data/runs-silver, data/judging-sets, data/judge-verdicts, data/runs-judged), which they left untracked.
  • The inspector opens on large comparisons. At 10,000 items and 40 arms it never showed its verdicts: its charts took the least and greatest of 400,000 values with Math.min(...values), which overflows the call stack. Past 500 items a run its charts now draw shaded bins instead of a dot each (they were 1.2 million dots), and its per-item table draws only the rows it shows (10, then more on request; "show all" up to 1,000 items), where it drew all of them and hid the rest (3.2 million elements). Found measuring S3 in a browser.
  • The catalog's pages are the same whatever the process's hash seed. The arms page's per-config rows came out in another order every build, and on the models page a model's best rank, when two of its configs tied, could come from either: both iterated a set. Found comparing two builds of one project; a test now builds under six seeds.
  • A goal's dataset notes with a comma were cut short. notes: first 200 test rows, all CNN; ... inside a {...} entry is YAML for notes: first 200 test rows and a stray key; seven goals (the tutorial's among them) showed half a note on their pages. The notes are quoted, and the goal schema now refuses a key a dataset entry does not have (validate V14 names it). Found by the data page's round trip.
  • A release cuts a hidden dataset's judged and re-scored runs too. The deployment's copy decided "hidden" for each folder directly under data/runs*, so a run a level deeper (runs-judged/<scorer>/<run>, runs-rescored/<scorer>/<source>/<run>) on a hidden dataset was copied whole, its rows' _meta (which a judging carries over from the source row) included. Each run is now decided by its own dataset. This repository has no hidden dataset, so its published catalog never carried any.
  • evh <command> --help names the command. 43 of the 67 commands printed the script behind them (evh run-promote --help said usage: promote_baseline.py).
  • evh validate survives a file that does not parse. A dataset, run, baseline or capture that is not valid JSON is named by V1, and every later check runs; before, the first check to read it ended validate in a traceback. A reference manifest, capture record or label set that does not parse is named by its own check.
  • A cancelled MCP call stops its command. The server waited for the command to finish, so a call a client gave up on kept running to its timeout and held one of the server's slots.

v0.7.2

The public MCP server's answers written ahead were empty. From 0.6.2 to 0.7.1 its goals, datasets, arms, models, references and runs-list answered as if the project held nothing, and 0.7.1's leaderboards written ahead were never written. A project's own server (evh mcp without --answers) and every command were not affected. No result moves.

Fixed

  • Answers written ahead are answered from the project's data. evh mcp --write-answers runs each command inside the project; the deployment passed EVAL_HOME as a relative path (_release/inspector), which each command read from inside the project, where there is no such folder. A relative EVAL_HOME or EVH_P_CACHE is now made absolute from where the caller stands before the command runs.
  • A broken write is no longer silent. --write-answers names what it could not write (a dataset with no runs, an answer too large, or a call that failed with its error) and exits non-zero when a call failed; the deployment's render also refuses answers whose goals do not list the release's goals, or that hold no leaderboard.

release2026-11-04

v0.7.1

Fixes from the fifth newcomer scenario (the first on a release, 0.7.0) and from releasing 0.7.0. A judge that returns empty replies no longer leaves a tree that fails evh validate; the commands say more about what they did and what they spent; the public MCP server answers a leaderboard at once. No committed run's scores move; three figures read differently (Changed).

Changed

  • family-test --round tests the round's leader against every other arm in play, without --a and --against (as pair-test --round picks its pair), and reads a re-score in place of the run it re-read, as the round does. A family test of a round can give a different p than 0.7.0's runs-only read.
  • The billed figure counts arm smokes. evh overview's billed tile and the catalog's include what evh arm-smoke spent (recorded in the model records), and the spend lists name it as "arm smokes".
  • runs-list --baselines shows the baseline's mean over its repeats, as every other view does; --json scores is that mean and a repeats column says over how many.
  • --json fields: the leaderboard's frontier gains dominated_by; evh goals --goal's last column is named decision (it was ""); the dry run gains input_tokens_counts; arm-smoke has --json.

Fixed

  • An empty judge reply is withheld like any other unparsed reply. A reasoning judge that spent its whole max_tokens thinking returned nothing; judge-score stored it as text and evh validate's V12 then failed on the harness's own record. Now it is withheld (its hash kept), V12 names the command that rewrites one stored before 0.7.1 (evh judge-score … --retry-unparsed), each unparsed reply says why (empty, cut off at the token limit, not JSON, not the expected shape), a pass whose replies were cut off ends with a HINT (raise max_tokens, or reasoning: {enabled: false}), and its progress lines arrive as they happen through a pipe.
  • evh arm-smoke prints each reply (its first 300 characters; --replies for all) and what it spent, and times a call that the adapter did not time.
  • evh run says whether "spent" is the provider's bill or the config's price table, prints no "warmed up in 0ms" for an arm with nothing to load, and counts the config's prompt in the dry run's input estimate.
  • rescore ends with a whole sentence that says when a re-score stands in for a run, and warns about outputs cut off at max_tokens. score-preview says when a goal holds no measured run to re-score.
  • silver-calibrate says what --ref-match and --arm-match take, with an example from your runs.
  • Leaderboards fit the terminal (the ranking metric first, the rest named; --wide for every column), and "dominated" says what it means (as good on all three, better on at least one) and by which arm.

v0.3.0

Re-measure what you already have. Stored outputs can now be scored again by LLM judges, as an optional pass that never touches a committed run: evh judge-score, for any text task you declare (what an item is, what the outputs are, the dimensions, the scale). The harness refuses a judge until the scorer names, for each judge, a committed run that measured it against human ratings; it runs at least two judges from different vendors blind, measures their position bias and noise, and stores every verdict so a rerun costs $0. The tutorial has an offline, $0 judging step (GUIDE step 10). Upgrading from 0.2.0 changes no committed run or score and adds no dependency. Design: ADR-0001; what it found here: the judging page.

Added

  • evh judge-score (and make judge-score). Re-measure an experiment's frozen outputs with a validated LLM judge, billed, cost-capped and resumable. It runs from the installed package in a project that has only its own data directory, scorer, prompt and runs: the prompt builder, reply parser, tau-b and Spearman, and an OpenAI-compatible judge client (LiteLLM proxy, OpenRouter direct, per-judge base_url / api_key_env, billed cost read from the response, retries) are in evaluation_harness.judging, with no dependency on examples/.
  • The judge scorer artifact (data/scorers/<id>.yaml): two or more judges from different vendor families, the task, the prompt (with its sha256), the protocol, a validation block and a cost cap.
  • Any text task, declared in the scorer. An optional task block names what each item is (source_label), what the arms wrote (output_label), the dimensions the judge scores and the scale; a prompt writes {n} where the number of outputs per call goes. Without a task block a scorer judges SummEval's news-summary task (ARTICLE, SUMMARIES, four dimensions, 1-5), byte for byte as before. A declared task is hashed into the judging set.
  • A judging step in the tutorial (docs/GUIDE.md step 10): harness/tutorial/scorers/tickets-judge-v1.yaml re-measures the tutorial's arms with two fake judges, offline and $0, through the refusal, the dry run, the pass and the leaderboard.
  • A validation gate. A scorer runs only if its validation block names a committed run for each judge whose metric equals the stated value (and is at least min_metric, when the scorer sets one) and whose model, temperature, reasoning, provider, max tokens, prompt file and prompt sha256 are the judge's. The gate checks that a validation exists and is current, not that it transfers to your outputs. Otherwise --unvalidated runs it and labels every number "unvalidated judge". provider: fake judges (offline, free, for testing a scorer) can never pass the gate.
  • Judging sets and stored verdicts. One item is the article plus every arm's output, arm identities hidden, order shuffled by a seed; the set is hashed into its id and frozen in data/judging-sets/. Every reply is stored per call in data/judge-verdicts/, with its scores, so a rerun resumes and re-reading costs $0; a reply that is not bare JSON scores, or repeats 8 consecutive words of the item or an output, is kept only as its hash, since a judge that reasons aloud can copy the source. A different arm set is a new set, never an append. A block retried with --retry-unparsed keeps the earlier calls' cost in its record.
  • Controls. A position check (a second shuffle that re-forms the blocks) and a noise check (a repeat on a subset), plus per-judge agreement and a self-family flag, in summary.json.
  • Adjudicated gold re-measurement (repository tooling, examples/_shared/adjudicate.py, not in the package): a committed adjudication file overwrites only the disputed items of a local gold reference set to make a new reference version, and rescore re-scores every run against it for $0, the old reference kept beside it.
  • Judge validation on published human ratings (repository tooling, not in the package): validate_judge_goyal.py (Goyal, Li & Durrett 2022) and validate_judge_zhang.py (Zhang et al. 2024, crowd ratings of 19 LLM-era summarisers) check a scorer's judges against people. The ratings are downloaded when the check runs, pinned by sha256, and never committed; the committed records hold article ids, the judges' replies and scores, and hashes; a reply that is not bare JSON scores, or repeats 8 consecutive words of the source, is kept only as its hash.
  • validate V11-V13. V11: every judging set's stored hash is the hash of its content. V12: every stored verdict names a real set, item, pass and block, and its n is that block's size, and every committed judge reply (verdicts and validation records) is bare JSON or kept only as its hash. V13: every judge scorer loads, is structurally valid (its task included), and its prompt file resolves and renders. They read the configured data directory.
  • judge-score judges every arm on the dataset by default. A scorer's arms_match, --match and --arms narrow it, and it warns when the arm set mixes config versions (_v1 and _v2 of one arm are judged as two arms).
  • A scorer's prompt.file resolves against the project root, then the scorer file's own directory, then (in a checkout of this repository only) the repository root.
  • Judged runs carry no reference_tier, since a judge reads no reference: the source run's tier is kept as judged_with.source_reference_tier, and leaderboard says the scores come from a judge, with its label.
  • A refused judge call stops the pass cleanly. A call refused, or still failing after its retries (a provider's own budget guardrail answering 403, for example), stops the pass the way the cost cap does: every stored verdict is kept, the partial result is projected and labelled, and the same command resumes.
  • Scorer checks. task.scale must be whole numbers, and a prompt with both {n} and SummEval's fixed count phrases is refused (the phrases would keep saying 16). V13 renders each prompt at 2 outputs, so a prompt that cannot be rendered fails there, not at run time.
  • Experiment-level results this enables are reported in the repository's reports (the summarisation experiment re-measured with two pairs of SummEval-validated judges, not confirmed by people on those outputs; AG News and DBpedia against adjudicated gold); none of them is in the package.

Changed

  • leaderboard's precision note no longer fires on values that are exact small-integer fractions (a mean of 1-5 ratings over two judges and four dimensions is in eighths); scores rounded on the way to disk still get it.
  • Nothing that scores a run changed: committed runs and their recorded hashes are untouched, and the committed summarisation judging set rebuilds from its stored verdicts with the same id.
