release2026-10-21

v0.3.0

Re-measure what you already have. Stored outputs can now be scored again by LLM judges, as an optional pass that never touches a committed run: evh judge-score, for any text task you declare (what an item is, what the outputs are, the dimensions, the scale). The harness refuses a judge until committed runs show it agrees with human ratings, runs at least two judges from different vendors blind, measures their position bias and noise, and stores every verdict so a rerun costs $0. The tutorial has an offline, $0 judging step (GUIDE step 10). Upgrading from 0.2.0 changes no committed run or score. Design: ADR-0001; what it found here: the judging page.

Added

  • evh judge-score (and make judge-score). Re-measure an experiment's frozen outputs with a validated LLM judge, billed, cost-capped and resumable. It runs from the installed package in a project that has only its own data directory, scorer, prompt and runs: the prompt builder, reply parser, tau-b and Spearman, and an OpenAI-compatible judge client (LiteLLM proxy, OpenRouter direct, per-judge base_url / api_key_env, billed cost read from the response, retries) are in evaluation_harness.judging, with no dependency on examples/.
  • The judge scorer artifact (data/scorers/<id>.yaml): two or more judges from different vendor families, the task, the prompt (with its sha256), the protocol, a validation block and a cost cap.
  • Any text task, declared in the scorer. An optional task block names what each item is (source_label), what the arms wrote (output_label), the dimensions the judge scores and the scale; a prompt writes {n} where the number of outputs per call goes. Without a task block a scorer judges SummEval's news-summary task (ARTICLE, SUMMARIES, four dimensions, 1-5), byte for byte as before. A declared task is hashed into the judging set.
  • A judging step in the tutorial (docs/GUIDE.md step 10): harness/tutorial/scorers/tickets-judge-v1.yaml re-measures the tutorial's arms with two fake judges, offline and $0, through the refusal, the dry run, the pass and the leaderboard.
  • A validation gate. A scorer runs only if its validation block names a committed run for each judge that has the stated metric, the judge's model, temperature, reasoning, provider, max tokens and prompt. Otherwise --unvalidated runs it and labels every number "unvalidated judge". provider: fake judges (offline, free, for testing a scorer) can never pass the gate.
  • Judging sets and stored verdicts. One item is the article plus every arm's output, arm identities hidden, order shuffled by a seed; the set is hashed into its id and frozen in data/judging-sets/. Every raw reply is stored per call in data/judge-verdicts/, so a rerun resumes and re-reading costs $0. A different arm set is a new set, never an append.
  • Controls. A position check (a second shuffle that re-forms the blocks) and a noise check (a repeat on a subset), plus per-judge agreement and a self-family flag, in summary.json.
  • Adjudicated gold re-measurement (repository tooling, examples/_shared/adjudicate.py, not in the package): a committed adjudication file overwrites only the disputed items of a local gold reference set to make a new reference version, and rescore re-scores every run against it for $0, the old reference kept beside it.
  • Judge validation on published human ratings (repository tooling, not in the package): validate_judge_goyal.py (Goyal, Li & Durrett 2022) and validate_judge_zhang.py (Zhang et al. 2024, crowd ratings of 19 LLM-era summarisers) check a scorer's judges against people. The ratings are downloaded when the check runs, pinned by sha256, and never committed; the committed records hold article ids, the judges' scores and hashes, and a judge reply that quotes the source text is not stored.
  • validate V11-V13. V11: every judging set's stored hash is the hash of its content. V12: every stored verdict names a real set, item, pass and block, and its n is that block's size. V13: every judge scorer loads, is structurally valid (its task included), and its prompt file resolves and renders. They read the configured data directory.
  • Experiment-level results this enables are reported in the repository's reports (the summarisation experiment re-measured with two validated judges; AG News and DBpedia against adjudicated gold); none of them is in the package.

Changed

  • prompt.file in a scorer resolves against the project root, then the scorer file's own directory, then (in a checkout of this repository only) the repository root. A committed scorer's repo-relative path resolves exactly as before.
  • judge-score judges every arm on the dataset by default. It used to default to arms whose config_id contains _n200_v1, this repository's naming, which found nothing in any other project. A scorer's arms_match, --match and --arms still narrow it.
  • Judged runs carry no reference_tier: a judge reads no reference. The source run's tier is kept as judged_with.source_reference_tier, and leaderboard says the scores come from a judge, with its label, instead of "scored against SILVER references".
  • A refused judge call stops the pass cleanly. A non-transient failure (a provider's own budget guardrail answering 403, for example) used to end judge-score with a traceback. It now stops the way the cost cap does: every stored verdict is kept, the partial result is projected and labelled, and the same command resumes.
  • judge-score warns when the arm set mixes config versions (_v1 and _v2 of one arm are judged as two arms).
  • A judge scorer's task.scale must be whole numbers, and a prompt with both {n} and SummEval's fixed count phrases is refused (the phrases would keep saying 16). validate's V13 renders each prompt at 2 outputs, so a prompt that cannot be rendered fails there, not at run time.
  • leaderboard's precision note no longer fires on values that are exact small-integer fractions (a mean of 1-5 ratings is in quarters or sixths); scores rounded on the way to disk still get it.
  • Nothing that scores a run changed: committed runs and their recorded hashes are untouched, and the committed summarisation judging set rebuilds from its stored verdicts with the same id.

release2026-10-20

v0.2.0

The first version meant to be installed rather than copied: pin a release tag, run evh, and your project's data stays in your project, never in the installed package. Runs now record which harness produced them, other tools' scores can be imported as runs, and the paired tests handle lower-is-better metrics.

Added

  • Installable package. pip install "evaluation-harness @ git+https://github.com/chipi/eval-harness@v0.2.0#subdirectory=harness" gives the evh command: every Makefile target, running the same scripts.
  • EVAL_HOME / EVAL_DATA_DIR. The project's data lives in the project, never in the installed package; the data root can be nested (for example data/eval/stats).
  • The harness identifies itself in every run. fingerprint.instrument.harness gains version, code_sha256 and installed.
  • evh import-run. Per-item scores produced by another tool become a run the significance tests read, with the source, the scorer and the sha256 of the imported bytes on the record.
  • --asc for pair-test and family-test. For lower-is-better metrics, "wins" and "ahead" count the lower score. The p-values were already two-sided and do not change.

Changed

  • validate's V9 evidence floors are read from <data>/validate_floors.json (project policy) instead of being hardcoded for this repository's run directories.
  • The family-test cache lives under the project root, not beside the code.

GitHub Release v0.2.0 ↗

release2026-10-19

v0.1.0

The harness as first published with its six worked experiments, before it was packaged: a copy you take into your project rather than install. Frozen, hash-checked datasets; one adapter function for your system; runs that record their data, prompt, code, model and build; each arm's own noise; paired tests with Holm correction that say separated or tied; billed cost beside quality; re-scoring from stored outputs for $0; validation that fails CI; baselines promoted only with a reason. Tagged afterwards, at the commit the site was deployed from on 2026-10-19 (9454f19), so a project that took a copy that week can name what it took. What changed between this copy and 0.2.0, including fixes that can move results: UPGRADING.
