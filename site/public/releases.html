v0.5.0

Two things to know before upgrading: the package now needs Python 3.10 or later, and it depends on the official MCP SDK (mcp>=2.3,<3). On 3.9, stay on v0.4.4. What you get: evh mcp, the project's read commands as tools for any agent (stdio on your machine, or --http for a team or the public), and a dataset page that shows what is inside a dataset without republishing its text. UPGRADING has the steps.

Added

  • evh mcp: the project's read commands as MCP tools, for an agent (stdio, the official SDK, RFC-018). Thirteen tools: overview, datasets, dataset-items, arms, goals, references, metrics, activity, search, inspect, rounds, runs-list, validate. Each call runs the command as a child process, so a tool answers what the command prints; each is annotated read-only; no tool writes project data, spends or runs a model (the one file a call writes is the p cache in the project's ignored .cache/, below). For Claude Code, in the project: claude mcp add evh -- evh mcp.
  • evh mcp --http: the same server for a team, or for anyone. Streamable HTTP, stateless, JSON responses: clients on every protocol revision since 2025-03-26 call tools without a session. The Host is checked against DNS rebinding (--allowed-host is required to bind beyond the loopback); --public leaves out the options that answer with an item's text, and the validate tool; --rate, --concurrent and --timeout bound the load; a missing required argument is refused before anything runs; --hooks takes a deployment's error reporting, tracing, metrics and analytics, in the inspector's shape. Each call is logged as one JSON line: the tool, its arguments' names (never their values), how it ended, its time; never the caller's address or user agent. --rate counts calls a minute per caller (an IPv6 caller by its /64), --rate-total for all callers together; over HTTP a caller has one call running at a time.
  • EVH_P_CACHE: the goals' paired tests kept on disk. Every evh command is a fresh process, so a view that shows the goals drew the same tests again each time (about 50 s on this repository's runs). With the variable naming a file, each estimated p is stored and read back exactly; evh mcp sets it to the project's ignored .cache/. goals, overview and arms answer in under two seconds after the first.
  • This repository's MCP server, https://evals.humancopilot.eu/mcp (the deployment, not the package): the six worked examples for any agent, read-only, without sign-in.
  • --json on the catalog's view commands (overview, datasets, arms, goals, references, metrics, activity, search, inspect): one object, {"command", "version", "result": {"blocks": [...]}}, each table as columns and rows of values, every other line as text. It is collected from the same calls that print the text, so the two cannot disagree. 0.7.0 gives each command its own result schema and retires this generic form: do not build on blocks.
  • What is inside a dataset, on its page and as a command. evh dataset-profile --dataset-id D, run where the dataset is materialized, writes data/profiles/D.json (schemas/profile.schema.json, checked by validate V1): the number of items and their words, the shape of each gold reference (labels and how many of each, entries per item, a record's fields, or words per reference), and per item its length, its gold and, when known, where it can be read at its source. A gold of labels (a few short values that repeat) is listed per item; any other gold is summarised, never listed. It holds no item text, which a dataset's licence may not let you redistribute, unless written with --with-text, which is refused unless git has committed every item's file (a project's own synthetic data). Commit the profile and the dataset page shows "what's inside" wherever the catalog is built; evh dataset-items --dataset-id D [--item ID] prints the same, and an item's text when it is materialized here.
  • An item's link to its source comes from the dataset: an item's source_url, or a data/sources/<dataset_id>.rows.json that a fetch or import step writes ({"source", "item_url", "rows": {item_id: {"row", "sha256"}}}), matched by the item's bytes, so an id that recurs in another dataset never takes its link. This repository's Hugging Face fetchers write one, so each item opens at its row in the dataset viewer.
  • inspect.html?…&item=ID opens that item once the comparison has loaded; a dataset page's inspect link uses it.
  • Adapter: dataset_profile(dataset), optional (RFC-003).
  • Every catalog page names its command, in its footer (evh goals --goal G, the inspector's from the arms picked). evh catalog --mcp URL names the same as an MCP tool call, with the server and how to connect (--mcp-howto); this repository's catalog passes its /mcp, and its header links to the site's MCP section.
  • evh dataset-profile --json and evh dataset-items --json print the profile inside the same envelope as the views, {"command", "version", "result": <the profile>}; the Makefile targets dataset-profile and dataset-items.

Changed

  • Python 3.10 or later. The official MCP SDK needs it, and every feature comes with one install, so the package's floor moves from 3.9 to 3.10 (CI tests 3.10, 3.11 and 3.14). On 3.9, pin v0.4.4.
  • A new dependency: mcp>=2.3,<3, which brings anyio, httpx2, mcp-types, opentelemetry-api, pydantic>=2.12, pyjwt[crypto], python-multipart, sse-starlette, starlette, typing-extensions, typing-inspection and uvicorn. No result moves.
  • A dataset id is a name, never a path. Every command that reads or writes data/…/<id>.json refuses an id that is not letters, digits, ., _ and - (or that holds ..); before, ../x read or wrote outside data/.
  • A param shown on a catalog page or by evh arms --arm hides a URL's user and password and a nested key named like a credential (headers: {Authorization: …}), as it already hid a top-level api_key.

Security

From two independent reviews before this release, each reproduced before it was fixed:

  • The inspector served any .txt under its data tree through /api/item?item=../../… (an item id was never checked; on main since 0.4.0). An item id is now a file's name, refused otherwise, in the server and the adapter.
  • The inspector's answers were cached by count, not size: a hundred distinct 40-arm questions took a 256 MiB container past its limit, and --warm alone did on this repository's data. The cache is bounded by the bytes it keeps (32 MB), keeps no refusals, takes no question over 4 KB, and --warm stops when it is three quarters full; the deployment's inspector has 384 MB (it peaked at 228 of 256 under load). Its rate key is an address, never a header's text.
  • evh mcp --http: a few parallel 4 MiB bodies killed the server; held GETs and ping floods cost memory no rate saw. Now --max-body, --max-connections, 8 open requests per caller, a 10 s deadline on a request's body (eight callers holding slow bodies took every connection), --request-rate, GET is 405, refusals do not count toward --rate-total, and --public answers are kept and their errors carry no paths. Values with NUL bytes or over 512 characters are refused.
  • The deployment: Caddy refuses a body over 64 KB on /mcp (and its handle line now adapts); nginx limits each visitor (20 requests a second, a burst of 200, 32 connections); the deploy checks the inspector is up and under 80% of its memory once --warm is done, and rolls back otherwise; the MCP hooks no longer export the SDK's own spans; the containers' /tmp caps files as well as bytes; render.sh's check for reference texts in a release could pass with 1,657 of them (a pipe's SIGPIPE) and refused the five tracked ones: it now compares against what git tracks; a deploy keeps two releases (the live one and the rollback), prunes at its start as well as its end, and refuses to start short of 2 GB or 300,000 inodes; the upload hard-links unchanged files again (no file ever linked: each release took ~69k new inodes).

Fixed

  • The deployment's release ships data/models.yaml (render.sh, and the item fields and profiles with it): from 0.4.2 it was never copied, so the deployed arms page called every model's weights unknown. tests/test_render_data.py fails when a part of data/ the adapter reads is not copied.
  • The CNN/DailyMail and SummEval fetchers deleted the committed gold manifest.json on every refetch; they now clear only the item files.
  • --hooks files with a module-level @dataclass failed to load (the module was not registered before it ran); they load as any other module now.
  • A page links only to http(s) URLs: a source_url or rows map that held javascript:… was written into an href.
  • The p cache reads an unreadable or non-UTF-8 file as no cache instead of failing the command, starts a new line after a torn one, and keys each p by how it was computed.
  • evh dataset-profile --with-text counts a file as tracked only once it is committed, not when it is merely staged.

release2026-10-25

v0.4.0

See your runs, not only tables of them. evh catalog builds static pages over a project's runs, and evh catalog-serve runs an inspector that tests chosen arms against a baseline and shows one item's outputs beside its reference. A project on the harness's layout needs no code; one with its own layout writes one adapter. Goals record what an evaluation is for; items carry the typed fields a project declares, and can live at a pinned URL. The paired test now lives in one place, evaluation_harness.stats, exact at 30 items or fewer. Upgrading can move a result only where pair-test or family-test ran on 30 items or fewer, in a wins count or an order on a lower-is-better metric, or where --exclude-dataset named a dataset whose items are not .txt files under data/sources/<id>/ (all below), and adds no dependency. Design: ADR-0002, ADR-0003; how to upgrade: UPGRADING.

This repository now deploys the harness on its own example experiments:

  • the catalog and run inspector are public at evals.humancopilot.eu/catalog;
  • the public site, the harness and its findings, moves from GitHub Pages to the same server;
  • the docs move to evals.humancopilot.eu/docs, and old /docs/ links redirect there.

The deployment files are in infra/ (runbook: infra/README.md). They are not part of the package.

The example experiments keep one record per arm, the latest: the rescored and re-parsed runs are folded into data/runs as derived runs, and DailyMail's bart_s is its fp32 run (coverage 0.4048; the fp16 run read 0.4039). CNN's bart_s stays the fp16 run, the one the judge's verdicts were made on. The reports state the current figures only; their correction logs are gone (git keeps them). Two published statements were stale and are restated: SciFact's qwen_s e5-first against the e5-first leader is +0.0178, p 0.10 (it read +0.0092, p 0.36, from the pre-fix run), and DBpedia's 56-item dev slice, over today's 28 arms, puts bert_base_fy alone at the top rather than 13 arms in a tie.

Added

  • The rest of the inspector and catalog in the terminal. Every page and view now has a command: - evh search TEXT is the catalog's search box, ranked the same way, with the command that shows each hit; - evh inspect --items is the per-item table (each arm's score and its Δ against the baseline); - evh inspect --analysis [--x METRIC] gives the analysis charts as numbers: spread per run, the difference from the baseline, and each arm's mean against a second metric.
  • pair-test --round rN tests within a round. A defaults to the round's leader, B to the baseline the round started from, and the metric to the goal's measure. An arm that is not in play is refused.
  • On the goal page: - each round has an inspect button that opens its arms against its leader (evh inspect --round); - every suggested command has a copy button; - a retired arm is greyed out.
  • Experiment rounds, optional (ADR-0004). Experiments go round on round: try some arms, keep what wins, drop what lost, change something, compare again. evh round-open --goal G --dataset D [--from rN] records what a round sets out to learn, what changed, the arms carried in unchanged (--keep) and those dropped with the reason (--retire ... --reason); arms join by naming it in their config (round: rN, recorded on the run). evh rounds --goal G reads the evidence the way the inspector does — the round's arms against its leader, its best against the previous round's best and against the baseline it started from, its spend against budget_usd — and suggests the next decision, each as the command that makes it: evh round-retire, evh rank-stability, evh round-close --conclusion ... --promote <run> (which promotes the baseline with the conclusion as its reason). A closed round refuses new runs; validate (V14) checks the records; leaderboard and family-test take --round. The goal page shows the rounds, newest first, with the open round's suggestions. The catalog stays read-only: decisions are commands. A project that never opens a round sees none of it.
  • A goal page leads with its answer. First the promoted baseline on each of its datasets and why (or "no decision yet", with the command that makes one), then what the goal is for, then on each dataset its references and its arms in groups by what they are scored against: gold, silver, a judge. Arms are ranked only within a group, and a group's leader is never an arm graded against its own outputs. A dataset page shows its baseline and reason, and the baseline's row is tagged. evh goals --goal and evh datasets --dataset-id say the same.
  • Everything the catalog and the inspector show is a command. evh datasets (one dataset: its versions, references and arms), evh references (one: who wrote it, from which run, what is scored against it), evh metrics, evh goals (one: its arms per dataset) and evh inspect --runs … (the inspector's verdicts, conditions, --where/--by on fields, --item for one item's outputs beside the reference). Same adapter, same computation: the numbers are the pages'. Each is also a make target.
  • The catalog says what every number is measured against. A metrics page (what each metric measures, which way is better, where it is recorded, which goals decide on it) and a page per reference (who wrote it, from which run, every arm scored against it); every metric and reference on the pages links there. Each arm's row says what it is scored against, and rows scored against silver, by a judge, or against the reference the arm wrote itself are tinted; a judged arm reads "judge <scorer>", no longer "gold". A goal page flags the arm that wrote the reference it is scored against, so it is never the leader. The inspector's charts section is "analysis", and its verdict rows carry the same tints. Actions are compact and tinted.
  • Long tables page. Every catalog table and the inspector's per-item table show 10 rows, with "show 10 more" and "show all"; the filter and the sort work over every row, and a link to a row opens the table at it. The verdict tables stay whole: their Holm thresholds are read together.
  • Dataset versions keep their lineage. evh dataset-create --dataset-id x_v2 --from x_v1 records where a version came from and the item ids it adds, removes and changes (derived_from in the dataset file); validate V2 fails a version whose parent is gone. The catalog links versions both ways with what changed, and a version no arm has run on yet gets a page when it is linked to one that has.
  • The inspector says whether the compared runs ran under the same conditions, from their fingerprints: the machine, library versions, the harness, the scorer (adapter code), the items and the reference's bytes. One line when all match; otherwise the fields that differ, arm by arm, with a warning when the scorer or the reference bytes differ (different measurements) or latency is compared across machines. A dataset page names each arm's machine when its arms ran on more than one.
  • METRIC_DESCRIPTIONS in an adapter, one sentence per metric, is recorded on every run (metric_descriptions in metrics.json) and refreshed by evh rescore; the catalog reads the adapter's current descriptions over the recorded ones, so describing a metric later needs no new run. The harness describes its own metrics (cost, tokens, latency, judge scores).
  • A run becomes a reference: evh reference-create --from-run <run_id> (make reference-create RUN=<run_id>). The usual way to get references is to run the expensive model as an arm, read its results, and score the cheaper arms against what it wrote. Until now that took a second paid pass (--config), whose outputs could differ from the run you read, and the reference did not say which run it came from. --from-run copies a finished run's outputs and calls nothing; the manifest records the run, its config, fingerprint, build and cost. It refuses what run-promote refuses (a dirty tree, an unknown build), an unfinished, derived or other-dataset run, and --tier gold (gold is what a person wrote or checked). With --not-redistributed only the manifest is committed: it records the command that rebuilds the texts from the run, and that command, on a checkout with the manifest alone, writes them again and checks them against its checksums without touching it.
  • reference-create refuses an empty output, and outputs that stopped at max_tokens, by either path (--allow-cut-off for outputs that end at the cap by design). A frontier arm at max_tokens: 80 wrote 19 of 20 summaries cut off mid-sentence and one empty reply, and they were frozen as the reference with no word.
  • The leaderboard marks the arm that wrote the reference it is scored against (arm *, and a note): that row is graded against its own outputs.
  • reference-create says when gold exists (new runs keep scoring against gold; how to rescore against the new silver), and to commit the reference before the next run: an uncommitted reference makes every later run dirty.
  • A newcomer scenario for every release (SCENARIO): a fresh project, the published docs only, a summariser and a classifier with small CPU models, cheap hosted LLMs, a frontier reference and a judge, browsed in the catalog, under $1. RELEASING runs it before the merge.
  • A goal weighs cost, quality and speed, and recommends (ADR-0006). Cost (USD per item, tokens beside it) and speed (latency p50 and p95) are built in; success_criteria.axes adds limits, another measure, role: ignore, or the project's own per-item metric in one line. A strategy says who is tied with the quality leader (balanced, the default: not separated by the paired test and within a margin, 2% of the leader unless the goal sets one; quality_first; frugal) and tie_break (default cost, then speed) picks among them. Limits come first; flagged and retired arms are never recommended, nor is an arm measured on fewer items than the rest of its group; identical scores are always tied; a missing number is "not recorded", and an axis a tied arm does not record cannot break the tie; speed is not compared across machines the runs recorded. Some groups show their leader and never recommend: a dataset marked decides: false, a silver group beside a gold one, and a group measured by unvalidated judges ("Shown, not recommended", with the reason). The helpers are public as evaluation_harness.axes. The goal page shows the decision with its reasons, an axis column per arm and quality against each axis as charts; the home page's glance a recommended column with cost and speed against the baseline; the dataset and arm pages cost and speed; the inspector's scatter cost and tokens. evh goals --goal and evh overview print the same. Guardrails are shown on the goal page and in the CLI. When the recommendation is not the promoted baseline, the goal page and evh goals --goal say by how much and whether the test separates them; with no eligible arm, they count the reasons. The goals page and evh goals count configs filed and show each goal's recommendation. Cost and speed metrics are their own kinds, with the goals that weigh them, and costs print to six places; chart names no longer overlap.

release2026-10-21

v0.3.0

Re-measure what you already have. Stored outputs can now be scored again by LLM judges, as an optional pass that never touches a committed run: evh judge-score, for any text task you declare (what an item is, what the outputs are, the dimensions, the scale). The harness refuses a judge until the scorer names, for each judge, a committed run that measured it against human ratings; it runs at least two judges from different vendors blind, measures their position bias and noise, and stores every verdict so a rerun costs $0. The tutorial has an offline, $0 judging step (GUIDE step 10). Upgrading from 0.2.0 changes no committed run or score and adds no dependency. Design: ADR-0001; what it found here: the judging page.

Added

  • evh judge-score (and make judge-score). Re-measure an experiment's frozen outputs with a validated LLM judge, billed, cost-capped and resumable. It runs from the installed package in a project that has only its own data directory, scorer, prompt and runs: the prompt builder, reply parser, tau-b and Spearman, and an OpenAI-compatible judge client (LiteLLM proxy, OpenRouter direct, per-judge base_url / api_key_env, billed cost read from the response, retries) are in evaluation_harness.judging, with no dependency on examples/.
  • The judge scorer artifact (data/scorers/<id>.yaml): two or more judges from different vendor families, the task, the prompt (with its sha256), the protocol, a validation block and a cost cap.
  • Any text task, declared in the scorer. An optional task block names what each item is (source_label), what the arms wrote (output_label), the dimensions the judge scores and the scale; a prompt writes {n} where the number of outputs per call goes. Without a task block a scorer judges SummEval's news-summary task (ARTICLE, SUMMARIES, four dimensions, 1-5), byte for byte as before. A declared task is hashed into the judging set.
  • A judging step in the tutorial (docs/GUIDE.md step 10): harness/tutorial/scorers/tickets-judge-v1.yaml re-measures the tutorial's arms with two fake judges, offline and $0, through the refusal, the dry run, the pass and the leaderboard.
  • A validation gate. A scorer runs only if its validation block names a committed run for each judge whose metric equals the stated value (and is at least min_metric, when the scorer sets one) and whose model, temperature, reasoning, provider, max tokens, prompt file and prompt sha256 are the judge's. The gate checks that a validation exists and is current, not that it transfers to your outputs. Otherwise --unvalidated runs it and labels every number "unvalidated judge". provider: fake judges (offline, free, for testing a scorer) can never pass the gate.
  • Judging sets and stored verdicts. One item is the article plus every arm's output, arm identities hidden, order shuffled by a seed; the set is hashed into its id and frozen in data/judging-sets/. Every reply is stored per call in data/judge-verdicts/, with its scores, so a rerun resumes and re-reading costs $0; a reply that is not bare JSON scores, or repeats 8 consecutive words of the item or an output, is kept only as its hash, since a judge that reasons aloud can copy the source. A different arm set is a new set, never an append. A block retried with --retry-unparsed keeps the earlier calls' cost in its record.
  • Controls. A position check (a second shuffle that re-forms the blocks) and a noise check (a repeat on a subset), plus per-judge agreement and a self-family flag, in summary.json.
  • Adjudicated gold re-measurement (repository tooling, examples/_shared/adjudicate.py, not in the package): a committed adjudication file overwrites only the disputed items of a local gold reference set to make a new reference version, and rescore re-scores every run against it for $0, the old reference kept beside it.
  • Judge validation on published human ratings (repository tooling, not in the package): validate_judge_goyal.py (Goyal, Li & Durrett 2022) and validate_judge_zhang.py (Zhang et al. 2024, crowd ratings of 19 LLM-era summarisers) check a scorer's judges against people. The ratings are downloaded when the check runs, pinned by sha256, and never committed; the committed records hold article ids, the judges' replies and scores, and hashes; a reply that is not bare JSON scores, or repeats 8 consecutive words of the source, is kept only as its hash.
  • validate V11-V13. V11: every judging set's stored hash is the hash of its content. V12: every stored verdict names a real set, item, pass and block, and its n is that block's size, and every committed judge reply (verdicts and validation records) is bare JSON or kept only as its hash. V13: every judge scorer loads, is structurally valid (its task included), and its prompt file resolves and renders. They read the configured data directory.
  • judge-score judges every arm on the dataset by default. A scorer's arms_match, --match and --arms narrow it, and it warns when the arm set mixes config versions (_v1 and _v2 of one arm are judged as two arms).
  • A scorer's prompt.file resolves against the project root, then the scorer file's own directory, then (in a checkout of this repository only) the repository root.
  • Judged runs carry no reference_tier, since a judge reads no reference: the source run's tier is kept as judged_with.source_reference_tier, and leaderboard says the scores come from a judge, with its label.
  • A refused judge call stops the pass cleanly. A call refused, or still failing after its retries (a provider's own budget guardrail answering 403, for example), stops the pass the way the cost cap does: every stored verdict is kept, the partial result is projected and labelled, and the same command resumes.
  • Scorer checks. task.scale must be whole numbers, and a prompt with both {n} and SummEval's fixed count phrases is refused (the phrases would keep saying 16). V13 renders each prompt at 2 outputs, so a prompt that cannot be rendered fails there, not at run time.
  • Experiment-level results this enables are reported in the repository's reports (the summarisation experiment re-measured with two pairs of SummEval-validated judges, not confirmed by people on those outputs; AG News and DBpedia against adjudicated gold); none of them is in the package.

Changed

  • leaderboard's precision note no longer fires on values that are exact small-integer fractions (a mean of 1-5 ratings over two judges and four dimensions is in eighths); scores rounded on the way to disk still get it.
  • Nothing that scores a run changed: committed runs and their recorded hashes are untouched, and the committed summarisation judging set rebuilds from its stored verdicts with the same id.
