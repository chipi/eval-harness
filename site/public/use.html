Use it · on your problem · offline in fifteen minutes

Measure your problem.

You do not need our benchmarks. You need a decision to make, a few dozen real inputs, and an afternoon. Write one adapter for your system; the harness brings frozen data, fingerprints, noise, significance and cost — the habits, enforced.

01The lifecycle

Eight things, one direction, and two optional passes.

Every evaluation here — ours and yours — moves through the same eight artifacts; re-measuring the stored outputs later, and the next round, are optional. Pick one to see what it is, where it lives and the command that makes it.

Sourcesyour inputs

Any files: tickets, transcripts, documents, prompts. Keep them under version control — an untracked input makes every run unattributable. Or what your system did in production, kept as a capture: each record hashed, and a dataset frozen from a selection of them.

lives in data/sources/ — or anywhere · data/captures/<id>/
$ evh capture --importer jsonl --query … --capture …
In the guide →
Datasetfrozen · sha256

The comparison contract: an item list with the hash of every item. Two runs on different datasets cannot be compared, and a changed input is a new version.

lives in data/datasets/<id>.json
$ evh dataset-create --dataset-id tickets_v1
In the guide → Ours, in the catalog →
Materializedhash-checked copy

A working copy, re-verified against the frozen hashes every time — so a run can never measure bytes the dataset does not describe.

lives in data/materialized/<id>/
$ evh dataset-materialize --dataset-id tickets_v1
In the guide →
Reference setssilver · gold

What each item is scored against: labels (a person's, a model's, a rule's) promoted on purpose, at the tier chosen then. Silver: consistent, not correct, often an expensive arm's labels, so the cheaper arms are measured by how close they come to it. Gold: the yardstick a decision rests on. Gold always wins, and every run says which it used.

lives in data/references/<tier>/<id>/
$ evh label-from-run · evh reference-promote
In the guide → Ours, in the catalog →
Armsone config each

One system under test: provider, model, prompt, settings, in a YAML file. Change one thing, bump the config_id — the fingerprint will prove what moved. An arm can name a model record, set up once where it runs, and is smoked on a few items before its full run.

lives in data/configs/*.yaml · data/models/<id>.yaml
$ evh arm-smoke --config …
In the guide → Ours, in the catalog →
Runsoutputs + fingerprint

One pass of an arm over the dataset: every output, every per-item score, billed cost, latency, and a fingerprint of instrument, data, deployment and settings. Repeat it to measure noise.

lives in data/runs/<run_id>/
$ evh run --config … --repeat 3
In the guide → Ours, in the catalog →
Testssignificant or not

The leaderboard with its significance block, paired tests, Holm-corrected families. A claim means significant, not scored higher.

lives in your terminal
$ evh family-test --dataset-id … --a … --against …
In the guide →
Baselinea decision + reason

The run future changes are measured against, recorded with why. Never edited: the next promotion replaces it and git keeps the old one — in six months, “why is this the baseline?” has an answer.

lives in data/baselines/
$ evh run-promote --run … --reason "…"
In the guide → Ours, in the catalog →
Re-measureoptional · later

The same frozen outputs, measured again without re-running an arm: new gold or a new code scorer for $0, or LLM judges (grading each output, picking the best, or comparing two), billed and capped, that the harness refuses until they are validated against people. Written beside the originals, never over them; the primary metric changes only by a recorded decision. A new scoring rule is previewed first, then re-scores a round, which records the scorer it is judged by.

lives in data/runs-rescored/<scorer>/ · data/runs-judged/<scorer>/
$ evh score-preview --goal … · evh rescore --goal … --round …
In the guide → Ours, in the catalog →
Next roundoptional · and on

A goal is answered in rounds: each says what it set out to learn, carries the arms that stay, retires the rest with why, and closes with a conclusion. Before deploy they narrow a field; after it the same goal goes on, on new dataset versions of what the deployed system decides.

lives in data/rounds/<goal>/r<n>.yaml
$ evh round-open --goal … --from r1
In the guide → Ours, in the catalog →
02Patterns

Your question is probably one of these.

Each maps to an eval in this repository you can copy — its adapter, its configs, its scorer — and change the data. The idea underneath all of them — build a private leaderboard for your own application instead of trusting a public one — is Chip Huyen's, from AI Engineering (influences).

arms = models, same prompt

Is the cheaper model good enough?

On DBpedia a 115× price difference was not shown to buy accuracy. Run both on your items; if they tie and the gap is one you can live with, the cheap one wins.

accuracy · cost per itemcopy: classification-dbpedia-14 ↗
arms = prompts, same model

Did my prompt change help?

Name the pair before you look, tune on a pilot slice, confirm on the held-out rest.

pair-test · holdoutcopy: summarization-cnn-dailymail ↗
arms = LLMs vs. a small fine-tune

Route or label tickets

A small model trained on your labels can match or beat LLMs run with one prompt — and part of its lead can be learning your labels' quirks. Read the disputed items.

accuracy · disputed goldcopy: classification-ag-news ↗
arms = retrievers and rerankers

Search and RAG retrieval

The answer is a ranked list over a corpus; the corpus is hashed into every fingerprint so two runs searched the same haystack.

nDCG@10 · recall@100copy: retrieval-scifact ↗
arms = extractors

Pull fields out of text

The answer is a set; matching and parsing are part of the instrument, and an unreadable answer must score zero, not be skipped.

set F1 · parse ratecopy: ner-few-nerd ↗
arms = judges, scored against people

Use an LLM as a judge

Score a few dozen outputs yourself, then measure how well each judge orders them the way you do. On SummEval the best reached 93% of an expert's agreement. Validated, a judge re-measures your arms' stored outputs (evh judge-score).

Kendall τ · human ceilingcopy: summeval-judging ↗
arms = generators

Summaries and generated text

Score against references, clip for length so verbosity cannot buy recall, and check silver against a gold slice.

coverage · ROUGEcopy: summarization-cnn-dailymail ↗
arms = the deployed one + candidates

Is my system still deciding well in production?

Capture what it decided, score its decisions as an arm against labels (a rule's over what happened next, or a person's), and pick the rows where it was wrong for the next version of the dataset you govern.

capture · arm-from-capture · pickcopy: triage-fleet ↗
a model record

Is this model set up right before I compare it?

Onboard it where it runs (its build, whether it reasons, JSON, determinism), then smoke the arm on a few items before its full run.

model-onboard · arm-smokeany example
no: re-score

My scoring rule was wrong: do I run everything again?

Preview what the new rule moves, then re-score the round at $0 from the stored outputs; the round records the scorer and why.

score-preview · rescoreany example
a baseline + CI

Catch regressions before release

Promote today's run as the baseline; compare every change against it with the noise floor you measured; validate in CI.

run-compare · validateany example
measure it

How many test items do I need?

Split your items into disjoint halves and see when two halves agree on the ranking — measured, not taken from a power table.

rank-stabilityany example
03Step by step

Seven steps and five optional ones, on a real example.

The tutorial kit ships six support tickets and summaries a person wrote. Every output below is what the command printed.

  1. Set up

    A new folder, the harness pinned to a release, and the tutorial kit copied in. Guide →

    $ pip install "evaluation-harness @ git+https://github.com/chipi/eval-harness@v0.7.0#subdirectory=harness"
$ evh init --tutorial
wrote    26 file(s), the tutorial kit under tutorial/

  2. Create a dataset

    Your inputs become a contract: an item list with a hash per item. Guide →

    $ evh dataset-create --dataset-id tickets_v1 --source-dir tutorial/tickets
data/datasets/tickets_v1.json  (6 item(s))

  3. Describe your arms

    One YAML per candidate. Change one thing; bump the id. Guide →

    $ cp tutorial/configs/tickets_*.yaml data/configs/

  4. Optional: set the model up first

    A record per model, a deployment per machine; onboarding checks its build, reasoning, JSON and determinism there. Guide →

    $ evh model-onboard llama3.1-8b --deployment laptop
ONBOARD PASS

  5. Run the best arm; optionally its outputs become the reference set

    Your best system answers first; its answers become a model's labels, promoted to silver, and the others are measured by how close they come. Guide →

    $ evh run --config data/configs/tickets_author.yaml
$ evh label-from-run --run … --set author_v1
$ evh reference-promote --dataset-id tickets_v1 --labels author_v1 --tier silver --reason … --by me
data/references/silver/tickets_v1: 6 of 6 item(s), silver, promoted from tickets_v1/author_v1

  6. Run the others — three times

    The spread is how far an arm disagrees with itself. Guide →

    $ evh run --config data/configs/tickets_lead2_noisy.yaml --repeat 3
overlap_f1     spread=0.029372   treat deltas below 0.029372 as noise

  7. Compare

    Read the significance block, not the row numbers. Guide →

    $ evh leaderboard --dataset-id tickets_v1
pairs distinguishable: 1 of 3

  8. Choose, and record why

    Promote with a reason that says what the tests showed; validate in CI. Guide →

    $ evh run-promote --run … --reason "leads on silver but differs significantly from neither arm at n=6"
VALIDATION PASSED

  9. Optional: the next round

    Carry what stays, retire what lost with why, close with a conclusion. The goal goes on, before deploy and after. Guide →

    $ evh round-retire --goal tickets_summary --round r1 --arm tickets_lead1_v1 --reason …
$ evh round-close --goal tickets_summary --round r1 --conclusion …
round r1 of tickets_summary closed

  10. Optional: when the scoring changes

    Preview what a new rule moves; then re-score the round at $0, or adopt the rule from the next round. Guide →

    $ evh score-preview --goal tickets_summary
recommended  tickets_lead2_v1

  11. Optional: make it golden

    A person's answers, imported as labels and promoted at gold; re-score every run against them for $0. Guide →

    $ evh label-import tutorial/gold --dataset-id tickets_v1 --set owner_gold --by owner
$ evh reference-promote --dataset-id tickets_v1 --labels owner_gold --tier gold --reason … --by owner
$ evh rescore --dataset-id tickets_v1 --reference-id gold/tickets_v1 --out data/runs-gold
NO detectable arm effect · pairs distinguishable: 0 of 6

  12. Optional: re-measure with a judge

    LLM judges re-read every arm's stored outputs. The harness refuses a judge nobody validated; the tutorial's are fake, so it runs labelled. Guide →

    $ evh judge-score --dataset-id tickets_v1 --scorer tickets-judge-v1 --unvalidated
data/runs-judged/tickets-judge-v1  (6/6 items, unvalidated judge)
04Bring your own

What you write. What you get.

You write

Five things in your project. Nothing else is yours to write.

your-project/
scripts/adapter.pycall_system() sends one input to your system; score() compares an output with a reference
data/sources/your inputs: real ones, sampled on purpose
data/labels/the answers: gold for a slice you can check, silver from a model you trust
data/configs/*.yamlone per candidate: model, prompt, settings, price
data/goals/*.yamlwhat it is for: the measure that decides, limits, how a tie is broken

The harness gives you

Ten things you would otherwise build, or skip.

Frozen datasetsby content hash, re-checked on every use
A fingerprint per runinstrument, data, deployment, settings
Each arm's noisemeasured, not assumed
Paired testsHolm-corrected: significant or not
Cost and latencybilled, beside quality
Re-scoring for $0from stored outputs; validation for CI
A recommendationper goal, with its reasons, beside the baseline
A catalogevery goal, dataset, arm and run, and an inspector (ours)
MCP toolsevh mcp for an agent (how)
Validated judgesoptional, refused until checked against people

Start on Monday

Seven steps, in this order.

  1. Write the question as a goal: can ticket routing move to the cheaper model?
  2. Collect real inputs; freeze them.
  3. Write gold answers for a slice yourself.
  4. Write the adapter; one config per candidate.
  5. Dry-run; set a cost cap.
  6. Run each arm three times; note its noise.
  7. Test the comparison you named; promote with a reason; put evh validate in CI.
