01The lifecycle

Eight things, one direction, and one optional pass.

Every evaluation here — ours and yours — moves through the same eight artifacts; re-measuring the stored outputs later is optional. Pick one to see what it is, where it lives and the command that makes it.

Sourcesyour inputs

Any files: tickets, transcripts, documents, prompts. Keep them under version control — an untracked input makes every run unattributable.

Datasetfrozen · sha256

The comparison contract: an item list with the hash of every item. Two runs on different datasets cannot be compared, and a changed input is a new version.

lives in data/datasets/<id>.json
$ evh dataset-create --dataset-id tickets_v1
In the guide →
Materializedhash-checked copy

A working copy, re-verified against the frozen hashes every time — so a run can never measure bytes the dataset does not describe.

lives in data/materialized/<id>/
$ evh dataset-materialize --dataset-id tickets_v1
In the guide →
Referencessilver · gold

What each item is scored against. Silver: a model wrote it — consistent, not correct; usually an expensive arm's run, promoted, so the cheaper arms are measured by how close they come to it. Gold: a person wrote or checked it. Gold always wins, and every run says which it used.

lives in data/references/<tier>/<id>/
$ evh reference-create --dataset-id … --from-run …
In the guide →
Armsone config each

One system under test: provider, model, prompt, settings, in a YAML file. Change one thing, bump the config_id — the fingerprint will prove what moved.

lives in data/configs/*.yaml
In the guide →
Runsoutputs + fingerprint

One pass of an arm over the dataset: every output, every per-item score, billed cost, latency, and a fingerprint of data, code, model and build. Repeat it to measure noise.

lives in data/runs/<run_id>/
$ evh experiment-run --config … --repeat 3
In the guide →
Testsseparated or tied

The leaderboard with its significance block, paired tests, Holm-corrected families. A claim means separated, not scored higher.

lives in your terminal
$ evh family-test --dataset-id … --a … --against …
In the guide →
Baselinea decision + reason

The run future changes are measured against, recorded with why. Never edited: the next promotion replaces it and git keeps the old one — in six months, “why is this the baseline?” has an answer.

lives in data/baselines/
$ evh run-promote --run … --reason "…"
In the guide →
Re-measureoptional · later

The same frozen outputs, measured again without re-running an arm: new gold or a new code scorer for $0, or LLM judges, billed and capped, that the harness refuses until they are validated against people. Written beside the originals, never over them; the primary metric changes only by a recorded decision.

lives in data/runs-rescored/ · data/runs-judged/<scorer>/
$ evh judge-score --dataset-id … --scorer …

02Patterns

Your question is probably one of these.

Each maps to an experiment in this repository you can copy — its adapter, its configs, its scorer — and change the data. The idea underneath all of them — build a private leaderboard for your own application instead of trusting a public one — is Chip Huyen's, from AI Engineering (influences).

arms = models, same prompt

Is the cheaper model good enough?

On DBpedia a 115× price difference was not shown to buy accuracy. Run both on your items; if they tie and the gap is one you can live with, the cheap one wins.

Route or label tickets

Search and RAG retrieval

Pull fields out of text

arms = judges, scored against people

Use an LLM as a judge

Score a few dozen outputs yourself, then measure how well each judge orders them the way you do. On SummEval the best judges reached 93% of an expert's agreement (the best of 24, chosen on the same articles; 92% held out), and an open-weight one at 1/23 of the leader's price was not separated from it. Pin the provider: one judge, run once on each of two providers, scored 0.0113 apart and billed 3.7× apart. Once validated, a judge can re-measure your arms' stored outputs (evh judge-score), on any text task you declare; validate it on outputs like the ones it will judge.

03Step by step

Eight steps and an optional ninth, on a real example.

The tutorial kit ships six support tickets and summaries a person wrote. Every output below is what the command printed.

  1. Set up

    A new folder, the harness pinned to a release, and the tutorial kit copied in. Guide →

    $ pip install "evaluation-harness @ git+https://github.com/chipi/eval-harness@v0.4.0#subdirectory=harness"
$ evh init --tutorial
wrote    24 file(s), the tutorial kit under tutorial/

  2. Create a dataset

    Your inputs become a contract: an item list with a hash per item. Guide →

    $ evh dataset-create --dataset-id tickets_v1 --source-dir tutorial/tickets
data/datasets/tickets_v1.json  (6 item(s))

  3. Describe your arms

    One YAML per candidate. Change one thing; bump the id. Guide →

    $ cp tutorial/configs/tickets_*.yaml data/configs/

  4. Run the best arm; its run is the reference

    Your best system answers first; the others are measured by how close they come — and the answers are labelled silver. Guide →

    $ evh experiment-run --config data/configs/tickets_author.yaml
$ evh reference-create --dataset-id tickets_v1 --from-run …
data/references/silver/tickets_v1  (6 item(s), tier=silver, $0.0000)

  5. Run the others — three times

    The spread is how far an arm disagrees with itself. Guide →

    $ evh experiment-run --config data/configs/tickets_lead2_noisy.yaml --repeat 3
overlap_f1     spread=0.029372   treat deltas below 0.029372 as noise

  6. Compare

    Read the significance block, not the row numbers. Guide →

    $ evh leaderboard --dataset-id tickets_v1
pairs distinguishable: 1 of 3

  7. Choose, and record why

    Promote with a reason that says what the tests showed; validate in CI. Guide →

    $ evh run-promote --run … --reason "leads on silver but separates from neither arm at n=6"
VALIDATION PASSED

  8. Then: make it golden

    Add answers a person wrote; re-score every run against them for $0. Guide →

    $ evh rescore --dataset-id tickets_v1 --reference-id gold/tickets_v1 --out data/runs-gold
NO detectable arm effect · pairs distinguishable: 0 of 6

  9. Optional: re-measure with a judge

    LLM judges re-read every arm's stored outputs. The harness refuses a judge nobody validated; the tutorial's are fake, so it runs labelled. Guide →

    $ evh judge-score --dataset-id tickets_v1 --scorer tickets-judge-v1 --unvalidated
data/runs-judged/tickets-judge-v1  (6/6 items, unvalidated judge)
04Bring your own

What you write. What you get.

You write

  • An adapter — call_system() sends one input to your system; score() compares an output with a reference.
  • Your inputs — real ones, sampled on purpose.
  • The answers — gold, for a slice you can check; silver from a model you trust for the rest.
  • One YAML per candidate — model, prompt, settings, price.
  • A goal — what the evaluation is for: the measure that decides, limits on cost and speed, how a tie is broken.

The harness gives you

  • Datasets frozen by content hash, re-checked on every use.
  • A fingerprint per run: data, prompt, code, model, build.
  • Each arm's own noise, measured.
  • Paired and Holm-corrected tests — separated or tied.
  • Billed cost and latency beside quality.
  • Re-scoring from stored outputs for $0; validation for CI; baselines with reasons.
  • A recommendation per goal, with its reasons, beside the baseline a person promoted.
  • A catalog of every goal, dataset, arm and run, and an inspector that tests arms against a baseline and shows one item's outputs.
  • Optional LLM judges that re-measure stored outputs, refused until validated against people.

Start on Monday

  • Write the question as a goal: can ticket routing move to the cheaper model?
  • Collect real inputs; freeze them.
  • Write gold answers for a slice yourself.
  • Write the adapter; one config per candidate.
  • Dry-run; set a cost cap.
  • Run each arm three times; note its noise.
  • Test the comparison you named; promote with a reason; put evh validate in CI.
