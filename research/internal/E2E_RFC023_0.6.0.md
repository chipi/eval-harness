The outcome rules are partly time-based: an item seen once and never again in 14 days is labelled `dismiss`. One

## What it found in the harness (fixed, with tests that fail without the fix)

The first pass (2026-11-01, before labels could accept more than one answer) found these four; this run found none.

1. **`wrong` in the rows view marked every labelled item** (57 of 57). It asked `same(a, b)`, a hook for two outputs,
   whether a label and an output agreed; a triage label is a bare disposition and an output its JSON. It now asks
   the adapter's own score (`correct` 0), else `same()` (d60462c5).
2. **`new` marked 116 of 117**: it compared dates (each new day was new). It compares choice and yes/no fields, and
   text fields with few values (d60462c5).
3. **Runs scored against a label set were invisible**: this repository's `.gitignore` ignored `data/runs-labels-*`,
   and the catalog reads only what git keeps (d60462c5).
4. **`validate` refused them** once they were kept: the run schema allowed `reference_tier` gold or silver only. It
   allows `labels`.

## What it found about the fleet

- **Production ran what was promoted** for every decision since 2026-09-01; the first day's 8 were another model.
- **The replay is not production, decision for decision** (85 of 117), and on what happened afterwards it does
  worse: right on 0.483 of the labelled items against production's 0.655 (separated, p 0.012). A hosted model at
  temperature 0 is not deterministic (the arm smokes say so), and the probes the replay reads are rebuilt for the
  decision's time. Score production by its recorded arm; the replay measures the config, not what was delivered.
- **Escalating a real problem now counts as right.** With the rules giving a fixed or later-filed problem
  `[file, escalate]`, production's escalations of real problems are no longer counted wrong: its share right rose to
  0.655, and the rows view's `wrong` fell to 20.
- **The four tickets picked** were all `evidence_level=exact`, a value no decision in the governed half has (none
  before the split had the probes' answers kept exactly). Production `cleanup`ed them where the outcome rules say
  otherwise.

## Live importers, verified against the source (2026-11-01, read-only)

The e2e above captured from files. The two network importers were then run for real through `evh capture`, and every
captured record was compared with the source system through a different path than the importer's own. Keys were
loaded from the mini's env files into the process only. The scripts are not kept in the repo.

**github, on chipi/orrery (536 issues).** Five captures were made: all issues, closed, open, two labels, and a window.
Each was checked against GitHub's REST API, while the importer itself reads GraphQL.

| Capture | Query | Captured | REST says | Same set |
| --- | --- | --- | --- | --- |
| all | `{}` | 536 | 536 | yes (11 GraphQL pages) |
| closed | `state: closed` | 489 | 489 | yes |
| open | `state: open` | 47 | 47 | yes |
| labels | `triage-fleet/filed`, `triage-fleet/escalated` | 50 | 50 | yes |
| any of three labels | actionable, stale-candidate, low-signal (20, 17, 5 issues, overlapping) | 35 | 35, their union | yes |
| window | since 2026-10-01, until 2026-10-20 | 26 | 26 | yes |

- **Fields.** All 536 records equal REST on title, body, created_at, url, labels, comment count, state, state_reason
  and closed_at.
- **Events.** For all 509 close and reopen events, the time and actor equal REST's issue events, in order. 410 of
  them have a comment beside them, and each is the same author's comment REST lists within 120 s.
- **Duplicates.** Six issues are closed as duplicates. For #560 to #563, the `duplicate_of` the record gives is the
  issue their comments name. #87 and #93 have no comments, so their target (#139, #77) was not checked independently:
  REST's timeline shows the close as `duplicate` but names no issue.

**langfuse, on podcast prod (`http://homelab:4000`).** The window was 2026-10-31, a whole day: 155 traces, so the
importer read four pages. The capture was made with `observations: true`.

| Check | Result |
| --- | --- |
| ids against the API's own listing of the window (paged independently, 100 a page) | 155 = 155, the same set |
| each record against `GET /api/public/traces/<id>`: name, environment, tags, latency, cost, session, release, metadata, input, output | all 155 equal |
| observations: list, order by start time, the 12 keys read | 750 generations, all equal |
| `name: litellm-acompletion` | 6 captured = the window's 6 of that name |
| the window's edges at a trace's own time T | in `since=T`, not in `until=T`; 78 + 77 = 155, no overlap |
| `source.url` | the key's project; `GET` on the host answers 200 |

- `created_at` is rewritten from `…29.201Z` to `…29.201000Z`. It is the same instant: the capture normalizes every
  time to UTC ending in Z (`_importers.py`, by design).
- Orrery's Langfuse projects hold almost nothing (dev 0 traces, prod 2, the newest 2026-10-16). The triage fleet's
  decisions are not in Langfuse; they come from its ledger files, as in the run above.
- The podcast prod env file names no `LANGFUSE_HOST`, so the host had to be given. A project's capture setup has to
  supply it.

- The round-3 local leader (DGX vLLM) was not run: it needs the GPU in its mode; the candidate is the best hosted arm.

  data in a browser.

- github: a repository whose issues have more than 100 comments, or more than 100 close and reopen events, was not
  tried. The importer reads the last 100 comments and the first 100 events; orrery's largest has 11 comments.
- Langfuse was not checked on a project the harness evaluates: neither Orrery project holds traces to evaluate.
