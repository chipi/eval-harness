# `data/corpora/` — documents an arm searches, as opposed to items it is scored on

Every other task in this harness scores an arm on the item it was given. Retrieval does
not: an item is a **query**, and the thing the arm must search is a corpus that is the same
for every item and every arm.

That makes a corpus three things it is easy to mistake it for, and none of them:

- **not `sources/`** — there is no one-file-per-item correspondence; 200 queries search
  5,183 documents
- **not `references/`** — it is not ground truth, it is the haystack
- **not `materialized/`** — it is not derived from anything in this repo, it is downloaded

## Layout

```
data/corpora/<corpus_id>/
    corpus.jsonl      one {"doc_id", "title", "text"} per line, sorted by doc_id
    manifest.json     corpus_id, n_docs, corpus_sha256, source recipe
```

`corpus.jsonl` is gitignored — third-party text, same rule as every other corpus here.
`manifest.json` is not committed either, because it is regenerated by the fetcher; what
travels between machines is the **download recipe in the example's `fetch.py`** plus the
`corpus_sha256` recorded inside every run that used it.

## Why `corpus_sha256` is not optional

Two runs over the same queries against different corpora agree on `dataset_id`,
`items_sha256`, `reference_id`, the adapter hash and every parameter. Nothing else in the
recorded fingerprint distinguishes them, and the corpus is where the answer actually lives.

So the corpus hash goes in the arm fingerprint, and it is computed over the sorted
`doc_id`-and-text bytes rather than the file, so re-downloading in a different order
produces the same hash and a genuinely different corpus does not.
